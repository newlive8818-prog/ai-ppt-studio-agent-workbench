# AI PPT Studio｜售前方案总师 Agent、证据先行内容生产与双层经验设计

## 1. 文档状态

- 状态：`已确认，研发目标合同`
- 确认日期：2026-08-14
- 适用产品：`AI PPT Studio Agent 原生工作台 / Skill App vNext`
- 适用范围：任务确认后的内容生产、内容内审、内容审核闭环，以及内容与视觉经验吸收
- 不改变：内容审核侧边栏已确认的连续全稿、逐页四选一、冻结批次、整体修改方案和全篇复审交互
- 不包含：内容审核侧边栏的视觉重设计和具体组件实现；该部分由“用真实案例重设计侧边栏”任务独立完成
- 上位基线：项目根目录的四份唯一研发基线

本设计取代下列旧合同：

1. 固定内容生产多智能体流水线；
2. 以 `persuasion proposition -> claims -> evidence` 为主轴的观点先行方法；
3. 强制目录框架确认；
4. 独立的整稿展开授权；
5. 结论型主张、结论型标题作为默认质量要求；
6. 当前项目、个人经验、稳定能力包三层经验模型；
7. 必须经过多项目候选晋级后才允许同类型经验影响下一次生产的慢速学习方式。

## 2. 问题判断

现有内容阶段返工多，并不主要是智能体数量不足，而是生产方法和责任结构存在偏差：

- 多个固定角色共享同一套观点先行方法，无法通过角色数量自动得到更可靠的结果；
- 先确定说服命题、核心主张和希望客户形成的判断，再寻找材料支撑，容易形成选择性取证；
- 结论型标题把未经证明的因果、价值、必要性和行动决定提前写成事实；
- 现状、问题、症状、原因、影响、约束、未知和方案要求没有形成完整推导；
- 多个生产角色切换增加上下文和协调成本，但责任主体不清；
- 框架确认与整稿展开授权让人承担了过多过程操作，没有提高首稿质量；
- 材料不足被误作停止条件，导致系统无法承担“方案先行、共同验证”的售前任务；
- 经验学习需要等待过多层级和晋级步骤，用户的明确反馈不能及时改善当前后续页面和下一份同类方案。

因此，Agent 数量不再是产品质量主张。质量必须由方法、证据、责任、独立硬门和真实结果证明。

## 3. 目标架构

内容阶段采用：

```text
1 个售前方案总师 Agent
+ 事实与证据硬门
+ 售前阅读与客户立场硬门
+ 按风险临时调用的专业顾问
```

### 3.1 售前方案总师 Agent

总师 Agent 是完整内容链的唯一生产责任主体，负责：

- 理解任务、受众、决策阶段、材料边界和商业边界；
- 重建事实、未知、冲突、证据缺口和禁止外推项；
- 建立客户决策语境；
- 说明现状、问题、症状、影响、原因假设和约束；
- 从问题推导方案要求；
- 建立问题、要求、方案、边界和验证动作的映射；
- 组织阅读优先的整套叙事和每页完整内容；
- 修复两个硬门提出的问题；
- 消化内容审核批次，形成整套修改方案；
- 在项目中实时学习内容反馈；
- 为项目完结复盘提供内容证据。

总师 Agent 可以调用专业顾问，但顾问只解决明确的风险问题，例如行业语义、复杂业务架构、数据口径或合规边界。顾问不是固定流水线节点，不能分散总师责任。

### 3.2 有限专业否决权

如果用户意图中的业务结论没有证据支持，总师 Agent 必须：

- 拒绝把它写成客户事实、页面标题或确定结论；
- 删除；
- 降级为 `材料推断`、`诊断假设`、`方案建议` 或 `待联合验证`；
- 或提出更安全的叙事方案。

即使用户坚持，该内容也只能作为当前项目商业意图或建议存在，不能穿过事实与证据硬门成为已成立的客户结论、能力证明、结果承诺或保证。

### 3.3 独立硬门

硬门审查方不得直接修改内容，只能输出：

- `passed`；或
- `failed` + 结构化修复要求。

总师 Agent 负责修复并重新送审。任何一个适用硬条件失败都不能被评分、平均、多数意见或其他优点补偿。

若产品声称“独立 Agent 审查”，必须保存真实的：

- `independentAgentInstanceId`；
- 独立上下文包及哈希；
- 输入内容版本及哈希；
- 输出审查记录。

如果运行时没有上述独立执行证据，只能准确称为“隔离审查任务”，不得宣称多 Agent 已经参与。

## 4. 证据先行内容方法

正式生产顺序为：

```text
任务与材料边界
-> 事实、未知、冲突和证据缺口
-> 客户决策语境
-> 现状与问题诊断
-> 从问题推导方案要求
-> 问题—要求—方案适配
-> 阅读优先叙事
-> 完整逐页内容
-> 两个独立硬门
-> 总师 Agent 自动修复
-> 内容审核侧边栏
-> G0
```

核心规则：

> 证据决定系统有权得出什么结论；证据不能在结论确定后被选择性地用来支撑预设观点。

### 4.1 取消两个默认人工前置动作

以下动作不再是正式内容生产的必需前置条件：

1. 目录或框架的独立确认；
2. 完整整稿展开的独立授权。

Mission 和材料边界确认后，总师 Agent 自动推进到完整内容、内部硬门和修复。框架、证据书、问题诊断和方案映射仍然可查看、可追溯、可被用户随时干预，但默认不阻断。

只在下列条件暂停：

- 两个权威来源对关键事实发生冲突；
- 存在多个会导向实质不同方案的诊断路径；
- 需要改变高影响范围、预算口径、承诺或商业边界；
- 在系统限制内无法收敛。

### 4.2 三种材料模式

材料不足改变的是证据身份和交付定位，不是能否继续。

| 模式 | 条件 | 允许的生产结果 |
|---|---|---|
| `material-backed` | 客户或项目证据相对充分 | 事实重建、问题诊断、方案适配和完整方案 |
| `mixed-evidence` | 证据部分充分 | 事实、推断、假设、建议、缺口和验证动作共同构成完整方案 |
| `proposal-led` | 当前没有客户材料 | 结构化诊断假设、方案建议、验证问题和联合行动方案 |

三种模式都可以：

- 继续生成完整内容；
- 通过内部硬门；
- 进入内容审核侧边栏；
- 被用户在 G0 确认。

缺少证据本身不是硬门失败。以下行为才失败：

- 编造事实、数字、案例或材料；
- 引用不存在的来源；
- 把假设或建议写成客户事实；
- 把未证明能力写成已验证的客户适配；
- 把预期效果写成保证或承诺。

材料不足时，总师 Agent 必须把缺口转化为：

- 诊断假设；
- 方案选项；
- 验证问题；
- 建议补充的材料；
- 联合验证动作。

不得只输出“请补充材料”后停止。

### 4.3 内容身份

正式内容使用以下统一身份：

- `来源事实`
- `材料推断`
- `用户已确认`
- `诊断假设`
- `方案建议`
- `待联合验证`
- `证据缺口`
- `禁止使用`

标题、正文、图表标签、备注、审核投影和 G0 证据必须使用同一身份语义。

## 5. 正式内容对象

### 5.1 `PresalesEvidenceBook`

记录：

- 事实；
- 来源与定位；
- 材料版本；
- 用户确认事实；
- 推断及推断依据；
- 冲突；
- 未知；
- 证据缺口；
- 禁止外推项；
- 被排除材料；
- 可用于哪些内容任务。

### 5.2 `CustomerDecisionContext`

记录：

- 受众与角色；
- 当前决策阶段；
- 客户当前正在处理的业务事项；
- 已知共识；
- 决策问题；
- 约束；
- 未解决问题；
- 本次方案可以帮助完成的判断或下一步工作。

不得记录未经证明的“希望客户接受的结论”。

### 5.3 `ProblemSolutionFitMap`

记录：

- 现状；
- 症状；
- 原因或原因假设；
- 业务影响；
- 约束；
- 未知；
- 从问题推导的方案要求；
- 解决方案组件；
- 问题—要求—方案映射；
- 方案边界；
- 可选路径；
- 验证事项与下一步动作。

### 5.4 `ReadingDeckBlueprint`

每页至少包含：

- `slideId` 和顺序；
- 页面任务与阅读问题；
- 中立标题；
- 全部可见文字；
- 内容身份；
- 证据引用；
- 分析、假设、建议或验证事项；
- 问题—方案映射；
- 与前后页的关系；
- 完整演讲备注；
- 阅读完整性；
- 当前材料模式；
- 内部硬门结果和修复历史。

### 5.5 `PresalesRevisionProposal`

只用于高影响变化，例如：

- 章节和页数大幅变化；
- 方案范围变化；
- 商业承诺变化；
- 多种诊断路径需要用户选择；
- 用户反馈之间存在无法自动裁决的冲突。

普通内容修订不新增人工确认节点。

### 5.6 旧对象的迁移身份

当前代码中的 `PresalesContentStrategy`、`ClaimEvidenceMap`、`DeckArgumentMap` 和 `SlideDraftSet` 可在一个兼容期内作为内部投影或适配器存在，但不再是目标方法的权威起点，不得继续以 `coreTension`、`persuasionProposition`、`claims[]`、`coreClaim` 或 `desiredCustomerJudgment` 驱动内容。

## 6. 两个内容硬门

### 6.1 事实与证据硬门

由确定性检查和必要的隔离语义审查组成，检查：

- 来源可解析、版本正确；
- 被排除材料未进入内容；
- 事实、推断、假设、建议和验证事项身份正确；
- 诊断可追溯；
- 没有选择性取证；
- 没有因果跳跃；
- 没有无证能力、结果和承诺；
- 问题、要求和方案可追溯；
- `mixed-evidence` 和 `proposal-led` 没有伪装成材料充分。

### 6.2 售前阅读与客户立场硬门

使用一个真实隔离审查实例即可，不再拆成五个固定内容审查角色。检查：

- 是否站在客户及其决策任务，而非供应商能力清单的立场；
- 现状和问题是否完整；
- 症状、原因/假设、影响、约束和未知是否区分；
- 问题—要求—方案是否真正映射；
- 标题是否中立；
- 是否存在观点先行或强行说服；
- 不读演讲备注时页面是否仍可独立理解；
- 整套方案是否连贯、无无意义重复；
- 风险、边界、验证事项和下一步行动是否明确。

## 7. 中立标题规则

标题只陈述：

- 事实对象；
- 材料范围；
- 业务事项；
- 问题领域；
- 方案组件；
- 工作阶段；
- 验证事项；
- 下一步工作项。

未经正文证据和分析成立，标题不得使用：

- 因果结论；
- 优越性、必要性或唯一性；
- 代替客户作出的行动决定；
- “必须、才能、决定、应该”；
- “不是……而是……”；
- “真正的竞争力”及类似强迫性表达。

判断可以进入正文，但必须明确身份，例如：

- `材料观察`
- `AI 分析`
- `诊断假设`
- `方案建议`
- `待联合验证`

## 8. 内容审核与 G0

本设计不重做已确认的内容审核侧边栏交互。内部通过后的完整内容继续采用：

- 宿主最大宽度连续全稿；
- 每页完整可见文字；
- 真实材料、来源、页码/区域和用途；
- 完整演讲备注；
- 阅读质量和跨页关系；
- 每页 `approved | modify | evidence | merge-or-delete`；
- 非认可判断必须填写意见；
- 全页完成后提交不可变审核批次；
- Codex 先形成整套修改方案；
- 用户确认修改方案；
- 总师 Agent 修改并重新运行必要硬门；
- 新版本全篇复审；
- 最终 G0 在聊天中对当前版本单独确认。

上游流程变化不改变上述审核交互：框架和全稿展开不再分别确认，但内部通过的完整内容仍必须进入同一内容审核页。

G0 必须继续满足：

- 可信宿主确认；
- 绑定当前内容版本；
- 绑定当前 revision；
- 一次性 challenge；
- 不从页面保存、批次提交、修改方案确认或 MissionConfirmation 推断。

## 9. 两层经验系统

经验系统只保留：

1. `same-type`：同类型经验；
2. `global`：全局经验。

产品制度、安全合同、事实边界和 Gate 规则不是第三层经验，也不能被经验自动改写。

### 9.1 两类经验域

每层都包含：

- `content`：内容经验；
- `visual`：视觉设计经验。

跨域关系作为经验关联记录，不新增经验层。例如“高密度问题诊断页需要先收敛信息结构再决定视觉表达”可以同时关联内容和视觉证据。

### 9.2 两种吸收节奏

#### 实时吸收

以下信号在当前轮次提炼并立即影响当前后续工作：

- 用户的修改、补证据、删并意见；
- 内容或视觉硬门失败；
- 被否定的标题、问题说明或方案映射；
- 被否定的页面层级、密度、模板感、图片和图表使用；
- PowerPoint 真实渲染暴露的视觉或工程问题；
- 用户接受的内容或视觉修订；
- 修改前后的可验证差异。

一次明确且有效的反馈即可进入同类型经验，并用于：

- 当前页面；
- 当前项目后续页面；
- 当前项目下一版本；
- 下一份匹配的同类型项目。

#### 项目完结复盘

每个项目在 G4 通过、正式交付或被用户明确关闭后，系统必须自动生成 `ProjectExperienceRetrospective`，不等待用户提醒、不新增人工审批。

如果项目中止或放弃，生成中止复盘，但不得把结果记录为成功。

如果复盘任务暂时失败：

- 不阻断已经完成的交付；
- 项目标记 `experience-retrospective-pending`；
- 系统自动重试；
- 不允许静默关闭且没有复盘记录。

### 9.3 同类型经验匹配

内容经验主要使用：

```text
方案任务 + 客户受众 + 决策阶段 + 材料模式 + 页面任务 + 业务问题类型
```

视觉经验主要使用：

```text
方案任务 + 阅读场景 + 受众层级 + 材料模式 + 页面类型 + 信息密度 + 品牌约束 + 交付环境
```

行业是辅助条件，不要求完全同客户或同行业，避免经验过窄。

### 9.4 全局经验进入规则

两条路径可以进入全局经验：

1. 用户明确表示“以后所有项目都这样做”或同义全局指令，立即进入全局经验；
2. 同一机制在至少两个不同类型项目中真实成功，且通过适用硬门、没有明确反例，自动进入全局经验。

视觉经验的成功不能只由“无溢出、可打开、可编辑、技术检查通过”证明；还必须有用户视觉认可、阅读质量、页面任务表达和真实渲染结果。

### 9.5 冲突、降级和回退

- 同类型经验出现反例：缩小范围或拆分为不同子场景；
- 全局经验出现明确反例：停止在冲突场景自动应用，并降为同类型经验；
- 经验项版本化、可禁用、可退休、可回退；
- 客户事实、数据、Logo、截图、品牌资产、具体整页造型和未授权素材不得成为可复用经验；
- 经验编译进任务上下文，不在运行时直接改写产品制度、事实硬门、角色权限或 Gate 合同。

### 9.6 `ProjectExperienceRetrospective`

至少记录：

- 项目类型签名；
- 材料模式、受众、决策阶段和交付环境；
- 内容成功机制；
- 内容返工、硬门失败和用户修改；
- 视觉成功机制；
- 视觉失败、模板感、密度和真实渲染问题；
- 修改前后证据；
- 用户接受结果；
- 新增、合并、拆分、升级、降级、禁用和回退的经验；
- 下一项目应该自动调用的经验。

| `FrameworkDiscussionService`、`content/framework-confirmation`、`content/full-deck-expansion-authorization` | 不再作为正式内容前置门；兼容读取历史 artifact，但新项目不要求 |
| `PresalesContentStrategy`、`ClaimEvidenceMap`、`DeckArgumentMap`、`SlideDraftSet` | 兼容期内部投影；新权威对象为 EvidenceBook、DecisionContext、FitMap、ReadingDeckBlueprint |
| `content_action_policy.py` 固定阶段与角色链 | 重写为总师自动生产、两个硬门和修复循环 |
| `ContentReviewService`、`PageDecision`、`ContentReviewBatch` | 保留，继续服务已确认侧边栏审核交互 |
| `ExperienceLevel.CANDIDATE/PERSONAL` 与三速晋级 | 迁移为 `same-type/global`，增加 content/visual 域、实时吸收和完结复盘 |
| Python Runtime、artifact refs、expectedRevision、事务和不可变历史 | 保留为权威写入基础 |
| Node MCP 薄适配、React 只读正式投影 | 保持 |
| G0–G4、可信宿主确认、G0 重开清理下游 | 保持 |
| 严格路线 B、Codex Presentations、ReleaseTargetPolicy | 保持；当前必需目标仍为 `macos-powerpoint` |

并行“真实案例侧边栏”任务可以继续实现审核交互，但不得把旧框架确认、整稿展开授权、结论型标题或固定多智能体重新写回目标合同。

## 11. 错误与恢复

目标系统至少区分：

- `CONTENT_CRITICAL_SOURCE_CONFLICT`
- `CONTENT_DIAGNOSIS_BRANCH_REQUIRES_DECISION`
- `CONTENT_HIGH_IMPACT_SCOPE_CHANGE`
- `CONTENT_EVIDENCE_GATE_FAILED`
- `CONTENT_PRESALES_READING_GATE_FAILED`
- `CONTENT_REVIEW_BATCH_INCOMPLETE`
- `CONTENT_REVIEW_BATCH_STALE`
- `CONTENT_REVIEW_BATCH_FROZEN`
- `CONTENT_REVISION_PLAN_NOT_CONFIRMED`
- `EXPERIENCE_RETROSPECTIVE_PENDING`
- `EXPERIENCE_SCOPE_CONFLICT`

材料不足不是错误码，也不能转成 `CONTENT_MATERIAL_REQUIRED` 之类的通用阻断。

所有失败必须保留：

- 上一份有效内容；
- 用户未保存输入；
- 当前 sourceVersion；
- 失败硬门和修复要求；
- 可恢复动作。

## 12. 验收标准

### 12.1 内容首稿

1. Mission 与材料边界确认后，不要求框架确认或整稿授权即可自动生成完整内容；
2. `material-backed`、`mixed-evidence`、`proposal-led` 都能走到完整内容审核；
3. 用户首次看到的内容已经通过两个硬门；
4. 标题中不存在未经证明的因果、必要性、唯一性和代客决策；
5. 现状、问题、影响、约束、未知、方案要求和方案映射完整；
6. 不读备注时，每页仍可独立阅读；
7. 无材料项目没有伪造客户事实、数字、案例、能力适配或效果承诺。

### 12.2 审查真实性

1. 硬门失败不能被评分或其他优点补偿；
2. 审查方不修改内容；
3. 若声称独立 Agent，存在真实独立实例、上下文、输入和输出证据；
4. 无独立执行证据时，产品准确显示为隔离审查任务。

### 12.3 审核闭环

1. 保留最大宽度连续全稿；
2. 保留四选一逐页判断和必填意见；
3. 全页完成后才提交不可变批次；
4. 总师 Agent 先提出整套修改方案；
5. 新版全篇复审；
6. G0 是独立、可信、版本绑定的最终确认。

### 12.4 经验吸收

1. 内容与视觉反馈都能形成经验；
2. 单次有效反馈在当前项目后续页面生效；
3. 下一份匹配项目能读取并记录同类型经验应用；
4. 两个不同类型项目成功或用户全局指令可形成全局经验；
5. 全局经验出现反例可以降级和回退；
6. 每个交付或关闭项目都有完结/中止复盘记录；
7. 客户事实和具体作品没有进入可复用经验。

## 13. 成功指标

不以 Agent 数量、角色运行次数或生成速度作为质量结果。持续记录：

- 首次内容审核的认可页比例；
- 首稿重大结构返工率；
- 现状/问题/方案说明类反馈数量；
- 观点先行和无证标题命中数量；
- 两个硬门的首次失败类型；
- 内容审核轮次；
- 同类型经验命中后的返工变化；
- 全局经验的跨类型成功、冲突、降级和回退；
- 视觉经验应用后的用户认可与真实渲染结果；
- 项目完结复盘生成率。

阈值通过真实项目建立，不在基线中虚构百分比。

## 14. 非目标

- 不重做本轮并行侧边栏视觉设计；
- 不把内容阶段变成传统表单或 PPT 编辑器；
- 不要求用户逐项确认 AI 的中间推理；
- 不暴露隐藏思维链；
- 不允许总师 Agent 自己越过硬门；
- 不把运行时经验升级成可以覆盖产品制度的规则；
- 不以更多 Agent 包装单实例角色切换；
- 不因材料不足停止生产。
