# 聊天、Widget 与专业审阅页 UI 分工设计

## 1. 文档状态

- 状态：`已确认`，作为 v1.5 UI 研发专项输入。
- 确认日期：2026-08-07。
- 适用产品：`AI PPT Studio Agent 原生工作台 / Skill App vNext`。
- 对应原型：[06-fullscreen-contract-review-exploration.html](../../../prototypes/06-fullscreen-contract-review-exploration.html)。
- 权威上位文件：
  - [产品需求基线](../../../../01-产品需求基线-v1.0.md)；
  - [系统详细设计](../../../../02-系统详细设计-v1.0.md)；
  - [UI 设计与交互规范](../../../../03-UI设计与交互规范-v1.0.md)。
- 本文解决聊天、轻量 Widget、专业审阅页和最终 PPTX 交付之间的职责边界，不改变内容多智能体、视觉多智能体、严格路线 B 和 G0–G4 的业务含义。

## 2. 设计结论

产品采用三个协同表面，而不是把全部流程塞进一个常驻侧栏或五个完整页面：

| 表面 | 核心职责 | 明确不承担 |
|---|---|---|
| Codex 聊天 | 理解目标、发送视觉样张、解释专业判断、承载复杂反馈、发送最终 PPTX 与交付说明、记录 G0/G3/G4 正式接受或修改意见 | 不作为结构化项目状态、合同正文和版本的唯一存储位置 |
| 轻量 Native Widget | 投影五个认知空间的当前状态、风险、待判断和成果入口；打开专业审阅页 | 不复制完整内容蓝图、整套视觉合同、联系表、大图质检或交付文件区 |
| 专业审阅页 | 连续阅读完整内容蓝图或整套视觉合同；对精确区块添加标记；显式保存标记 | 不提供返回聊天、顶部版本历史、视觉样张画廊、PPTX 下载、G4 验收或完整制作工作台 |

三个表面共享同一项目真相源。聊天消息、Widget 投影和专业审阅 HTML 都不是第二套业务数据。

## 3. 五个认知空间与三个 UI 表面的关系

五个认知空间继续稳定存在，但它们是领域信息架构，不等于五个独立完整页面：

| 认知空间 | Widget 投影 | 专业审阅页 | 聊天 |
|---|---|---|---|
| 项目总览 | 当前目标、AI 判断、最大风险、待判断 | 无独立长文档 | 建立任务、解释判断、处理复杂变更 |
| 材料工作台 | 材料数量、解析状态、冲突、缺口 | 无独立长文档 | 上传材料、补充上下文、处理来源冲突 |
| 内容蓝图 | 当前阶段、内部通过状态、批注数、打开入口 | 完整内容蓝图连续阅读与标记 | 解释修改、记录 G0 接受或重开 |
| 视觉设计 | G1/G2 状态、合同版本、批注数、打开入口 | 整套视觉合同连续阅读与标记 | 发送视觉样张、讨论审美、记录 G3 接受或重开 |
| 制作与交付 | 构建阶段、四门状态、阻断项、最终文件是否已发送 | 不建设独立验收页 | 发送 PPTX、预览和必要报告，记录 G4 接受或修改意见 |

## 4. Codex 聊天设计合同

### 4.1 视觉样张

- Image 2 探索图、Presentations 原生锚点页预览和必要的前后对比直接发送到聊天。
- 每次样张消息必须标明项目、页面、版本、样张身份和用户需要判断的问题。
- 样张不是合同真相源；其对应的设计规则、文字和范围仍保存在 VisualContract 与项目产物中。
- 聊天可以解释样张与视觉合同的关系，但不得要求用户在多个无差异候选间做内部设计团队本应完成的选择。

### 4.2 复杂反馈与专业治理

- 跨页面、改变叙事、审美原因不清、涉及事实/方案边界或需要重新推理的反馈在聊天中完成。
- AI 先形成 `FeedbackGovernanceRecord`，再给出真实问题、反例、范围、保持不变项和更优建议。
- 用户反馈不是自动成立的全局规则；F2/F3 扩大执行前必须经过用户裁决。

### 4.3 正式 Gate

- G0、G3、G4 仍是正式用户检查点。
- 用户完成专业审阅并保存标记后，在聊天中表达接受、修改或继续讨论；系统再调用正式 Gate 写入契约。
- 保存标记不等于确认 Gate，关闭审阅页也不等于确认 Gate。
- G1/G2 仍为系统内部质量门，不在聊天或页面制造用户选择负担。

### 4.4 最终交付与 G4

- G4 前，系统先完成整套 PPTX、目标 PowerPoint 实机导出和四门内部验收。
- Codex 在聊天中发送可下载的 PPTX 文件，并按风险附上必要的预览、字体/平台说明、来源或验收摘要。
- 用户在聊天中接受成稿或提出修改；系统记录 `G4 accepted` 或重开受影响范围。
- 不再建设独立“完成验收并交付”页面，也不在 Widget 中重复下载区和联系表。

## 5. 轻量 Native Widget 设计合同

### 5.1 页面使命

让用户在 Codex 工作过程中快速看到项目是否在轨、当前最大风险、是否需要判断，以及去哪里查看完整内容或结果。

### 5.2 信息结构

1. 项目与同步状态；
2. 当前认知空间；
3. 一句话当前结论；
4. 最大风险或待判断；
5. 当前成果和版本状态；
6. 一个主操作。

### 5.3 主操作路由

- 内容蓝图达到 `user-reviewable`：`打开内容审阅`。
- 视觉合同达到 G1/G2 内部通过：`打开视觉合同`。
- 制作中：只显示阶段、四门状态和是否可离开；不显示完整联系表。
- 最终文件已生成：显示“PPTX 已发送到聊天”及发送时间，不复制文件下载按钮。
- 出现高影响开放问题：显示 `处理当前判断`，由 Codex 聊天承接。

### 5.4 禁止

- 不复制完整内容蓝图或视觉合同；
- 不嵌入缩小版 PPTX 联系表或大图质检；
- 不展示常驻版本历史；
- 不把“回到聊天”作为页面内导航按钮；
- 不把宿主侧栏宽度不足转换成强制拖宽提示。

## 6. 专业审阅页设计合同

### 6.1 页面使命

为内容蓝图和视觉合同提供一个正文优先、连续阅读、可精确标记的审阅表面。页面只做阅读和标记，不复制聊天与交付职责。

### 6.2 打开方式

- 默认由 Codex 或 Widget 在右侧宿主浏览区/侧栏打开。
- 同一响应式页面可以扩展到更宽的 PC 或全屏视口；扩展只是阅读空间变化，不是第二套产品模式。
- 宿主无法保持侧栏时，降级为独立浏览页；项目状态和保存契约保持不变。
- 页面内不提供“返回聊天”按钮。侧栏关闭、宿主布局或浏览器窗口负责退出；聊天本身始终是并行交互面。

### 6.3 Header

- 统一约 64px 单行。
- 始终保留：产品标识、内容审阅/视觉合同切换、目录、标记、`保存标记`。
- `保存标记` 位于右上角，是唯一强主操作。
- 空间不足时依次隐藏英文副标题、长保存状态和项目长标题。
- 不显示版本历史入口、不显示返回聊天、不显示 G0/G3/G4 确认按钮。

### 6.4 目录

- 所有视口首次打开均默认折叠；不恢复上次打开状态。
- 不保留常驻列或窄轨道。
- 点击顶部目录按钮后从左侧覆盖打开，不改变正文宽度、横向位置或滚动位置。
- 点击条目完成定位后自动关闭；背景、关闭按钮和 `Escape` 均可关闭。
- 目录与标记抽屉互斥。

### 6.5 正文

- 内容审阅按最终页序连续展示全部可见文字、讲解稿、事实身份、来源、材料和状态。
- 视觉合同按最终页序连续展示 Deck Design System、每页完整文字绑定、构图与信息层级、素材路由、可编辑边界、字体/颜色/图片规则和硬验收条件。
- 不使用逐页 Tab、轮播、卡片墙、摘要、省略号、行数截断或 hover 才显示全文。
- 视觉样张在聊天发送；专业审阅页只保留样张版本引用、内部通过身份和必要的文字证据摘要，不建设样张画廊。

### 6.6 标记与保存

- 用户可以标记整个页面、合同字段或选中文字。
- 每个标记必须绑定：项目、审阅类型、源版本、目标锚点、选中文字、用户意见和创建时间。
- 未保存标记在刷新或关闭前必须明确提示；保存成功后显示持久化回执。
- `保存标记` 批量写入当前未保存标记，失败时保留本地草稿并允许重试。
- 保存后标记进入 `saved/pending-governance`，不得直接显示“规则已采用”。
- 保存标记不自动覆盖合同，不自动确认 G0/G3，也不自动修改稳定经验。

## 7. 制作与交付状态投影

UI-05 继续作为“制作与交付”认知空间标识，但不再是完整页面：

### 7.1 Widget 可显示

- 当前构建阶段；
- 已完成页数/总页数；
- 业务语义、视觉完成度、排版工程、目标软件渲染四门状态；
- 一个最高影响阻断项；
- 当前生产平台与 PowerPoint 实机证据是否齐全；
- 最终文件是否已发送到聊天及时间。

### 7.2 不显示

- Gate Strip；
- 全稿联系表；
- 选中页大图与多版本切换；
- 完整问题队列和技术日志；
- 交付文件下载区；
- `完成验收并交付` 按钮。

这些系统证据仍需生成和持久化，但不被重复包装成独立用户工作台。需要检查时由 Codex 按问题在聊天中发送相应证据。

## 8. 数据与系统契约

### 8.1 唯一真相源

- 内容真相源：权威 ContentBlueprint/Markdown 与结构对象。
- 视觉真相源：DeckDesignSystem、SlideVisualContract 与 VisualContract。
- 交付真相源：PresentationBuild、TargetRenderEvidence 与不可变交付产物。
- HTML、Widget 和聊天消息均为投影或交付通道。

### 8.2 ReviewMarkSet

```json
{
  "markSetId": "uuid",
  "projectId": "uuid",
  "reviewType": "content|visual",
  "sourceVersion": "artifact-version",
  "revision": 1,
  "status": "draft|saved|pending-governance|governed|resolved",
  "marks": [
    {
      "markId": "uuid",
      "targetAnchor": "string",
      "selectedText": "string|null",
      "comment": "string",
      "createdAt": "ISO-8601"
    }
  ]
}
```

### 8.3 必要工具契约

- `render_ai_ppt_review`：按项目、内容/视觉类型和版本返回专业审阅资源。
- `save_review_marks`：带 `expectedRevision` 批量保存 ReviewMarkSet，返回保存数量、新 revision 和治理状态。
- `get_delivery_status_projection`：只返回 Widget 所需轻量状态，不默认返回大图和全量日志。
- `record_chat_delivery`：记录发送到聊天的样张、PPTX、预览和说明的消息/产物引用。
- `confirm_gate`：G0/G3/G4 只能由 Codex 基于用户明确表达调用；专业审阅页的保存动作不得直接调用。

## 9. 状态与失败

### 9.1 专业审阅页

- 加载：显示文档身份和骨架，不阻塞 Header。
- 源版本过期：显示“当前审阅版本已更新”，保留未保存标记并要求合并，不静默迁移锚点。
- 保存失败：保留草稿、错误原因和重试；不清空文字。
- revision 冲突：显示冲突版本和受影响标记，不覆盖他人/AI 已保存结果。
- 宿主能力不足：保持同页降级，不显示强制拖宽遮罩。

### 9.2 最终交付

- PPTX 未达到 G4 前置条件：聊天只说明仍在内部修复，不发送伪最终文件。
- 文件发送失败：保留产物引用与上一有效文件，重试消息通道，不重新构建 PPTX。
- 用户提出修改：G4 保持未接受，按影响范围重开；聊天中明确上一有效版本仍保留。

## 10. 研发拆分建议

1. 建立三表面路由和共享 `activeContext`。
2. 将 Widget 收口为五空间轻量投影与专业审阅入口。
3. 将现有 Review Renderer 升级为内容/视觉双模式响应式审阅资源。
4. 实现 ReviewMarkSet、批量保存、revision 冲突与刷新恢复。
5. 移除专业审阅 Header 的版本历史、返回聊天和 Gate 确认动作。
6. 将原 UI-05 联系表、大图质检和交付区降为内部证据，不再暴露为完整页面。
7. 实现聊天样张发送、PPTX 交付、消息引用和 G0/G3/G4 记录。
8. 完成宿主侧栏、宽屏扩展和独立页面降级验收。

## 11. 验收标准

1. 1440、1000 和 760px 视口打开专业审阅页时目录默认关闭，Header 约 64px 单行，无横向溢出。
2. 三种视口都可连续阅读完整内容蓝图和视觉合同；长中文、长文件名和无空格字符串可换行。
3. 目录以覆盖方式打开，前后正文宽度、横向位置和滚动位置不变；目录与标记抽屉互斥。
4. 右上角可保存页面、字段和选中文字标记；刷新后已保存标记仍存在，未保存失败草稿不丢失。
5. 专业审阅页不存在返回聊天、版本历史、G0/G3/G4 确认、PPTX 下载和最终验收入口。
6. Widget 不展示完整合同、联系表、大图质检和交付文件区，只投影状态和入口。
7. 视觉样张由聊天发送且带项目/页面/版本身份；专业审阅页不重复建设样张画廊。
8. 最终 PPTX 由聊天发送，用户在聊天中的接受或修改能够正确记录 G4 或重开范围。
9. 聊天、Widget 和专业审阅页读取同一 revision；任一表面不得形成第二套状态。
10. 宿主无法保持右侧侧栏时可打开同一独立审阅页，保存行为和项目状态完全一致。

## 12. 明确不做

- 不建设独立 Web 产品或第二套账号系统；
- 不将专业审阅页扩展为完整 PPT 编辑器；
- 不在页面中复制聊天、视觉样张和最终文件交付；
- 不因 UI 收口删除系统内部的不可变版本、联系表、目标渲染和质量证据；
- 不把宿主当前支持右侧栏写成永久平台保证。
