# AI PPT Studio 反馈、优秀案例与经验进化治理设计

> **文档身份：历史，经验层级已废止。** 2026-08-14 起，当前项目/个人经验/稳定能力三速模型、候选晋级后才应用的慢速方式不再有效。经验只有同类型与全局两层，覆盖内容和视觉，并要求实时吸收与项目完结主动复盘。当前权威设计见 [售前方案总师 Agent、证据先行内容生产与双层经验设计](./2026-08-14-presales-chief-agent-content-and-experience-design.md)。

**日期：** 2026-08-05

**状态：** 历史，经验层级已废止；不得据此创建新实现

**适用范围：** 内容、视觉和 PPT 工程阶段的用户反馈治理；优秀案例、参考案例、成功成品和失败成品的学习；个人经验与稳定场景能力进化

**权威输入：** 项目根目录四份唯一研发基线；发生冲突时以更新后的产品需求基线为准

**兼容基础：** 复用现有 `ExperienceStore` 的候选经验、推荐、应用、评价、晋级、禁用和回滚能力；本设计扩展其产品语义和治理入口，不把既有测试结果当作真实项目成熟证据

现有实现中的“两项目成功晋级”继续作为已实现、可测试的默认策略，但不再作为 v1.3 已冻结产品阈值。最终晋级项目数、观察周期和降级阈值均标记为 `待验证`，必须依据真实项目证据另行确认。

## 1. 目标

把用户反馈从“直接修改指令”升级为“需要专业诊断的高价值信号”，把用户优选案例、普通参考案例、已接受成品和失败成品纳入同一经验入口。系统既要快速改善当前项目，也要通过受治理的跨项目学习持续提升所有专业智能体的内容能力、设计品味、审查能力和工程质量。

## 2. 核心原则

1. 用户反馈不是自动成立的规则。
2. AI 必须识别反馈所指向的真实问题、反例、范围和更优解决方案。
3. 用户拥有当前项目的最终裁决权；事实真实性、安全和系统硬约束不能被覆盖。
4. 用户坚持的特殊决定只成为当前项目约束，不自动进入跨页面或跨项目经验。
5. 原始反馈、项目修改和长期学习是三种不同状态，必须分开保存。
6. 用户认为优秀只证明偏好价值，不自动证明专业普适性。
7. 优秀案例和失败案例必须提炼机制、适用条件、证据、反例和失效边界。
8. 项目修改成功不等于经验成立；候选经验必须在匹配场景中继续验证。
9. 所有智能体按角色获得不同经验切片，不能共享同一份未经裁剪的记忆。
10. 稳定 Prompt、角色合同和场景能力包只通过治理发布新版本。

## 3. 反馈治理智能体架构

### 3.1 固定治理角色

| 中文正式名称 | 主要职责 | 不承担 |
|---|---|---|
| 反馈治理编排智能体 | 接收反馈、定位对象、判断范围、调用专业会诊、维护状态和输出正式治理记录 | 不替内容、视觉或工程专家决定专业结果 |
| 反馈反例审查智能体 | 检查局部意见被扩大后是否产生反例、例外、质量退化或范围污染 | 不直接执行修改 |
| 经验提炼智能体 | 从反馈、优秀案例、成功与失败成品中提炼偏好、机制和失败模式 | 不把整套案例复制为规则 |
| 经验适配审查智能体 | 检查经验与目标场景、听众、页面任务和条件是否匹配 | 不允许错误场景应用计入成功证据 |
| 经验进化治理智能体 | 管理候选、个人经验、发布候选、降级、禁用和回滚 | 不在运行时自动改写稳定能力包 |

### 3.2 专业会诊路由

- 内容反馈：调用售前内容策略、证据、叙事或专业表达相关智能体；
- 视觉反馈：调用售前视觉策略、视觉艺术指导、编辑设计、信息设计或图像艺术指导相关智能体；
- PPT 实现反馈：调用 PPT 工程和 PPT 工程审查智能体；
- 跨阶段反馈：调用多个专业角色，由反馈治理编排智能体汇总外化结论。

## 4. 两条独立链路

### 4.1 项目执行链

```text
原始反馈
→ AI 专业诊断
→ 治理后的反馈结论
→ 用户必要时确认
→ ContentChangeSet / VisualChangeSet
→ 修改与专业复审
→ 用户评价修改结果
```

项目执行链只回答“当前项目应该如何修改”。

### 4.2 经验进化链

```text
已治理反馈
+ 修改前后证据
+ 专业复审结果
+ 用户结果评价
→ 复用价值判断
→ 候选经验
→ 跨项目匹配应用
→ 成功/失败评价
→ 个人经验
→ 稳定能力发布候选
```

经验进化链只回答“系统以后应该学到什么”。两条链共享来源引用，但不得合并状态或自动越级。

## 5. F0–F3 反馈分级

| 级别 | 定义 | 示例 | 默认处理 |
|---|---|---|---|
| F0 明确局部修正 | 事实清楚、范围局部、低风险且可撤销 | 错别字、明显错位、错误裁切、遗漏来源 | 专业检查后直接修复并复审 |
| F1 局部主观偏好 | 用户感受到问题，但解决方式未必准确 | 太挤、不好看、信息不够清楚 | AI 诊断根因，形成更优局部实现并展示回执 |
| F2 跨页面或项目级规则 | 反馈将扩大到页面家族、整套或当前项目 | 后续页面禁止线段、所有案例固定三栏 | 检查反例和代价，用户确认治理后的规则后执行 |
| F3 专业冲突或高影响反馈 | 涉及事实、叙事、方案边界、品牌、最低质量或工程合同 | 删除关键证据、改变方案承诺、牺牲可编辑性 | 暂停执行，展示冲突和替代方案，等待用户裁决 |

用户不需要为每个 F0/F1 再次确认；F2/F3 必须显示治理结论和影响范围。事实真实性、安全和系统硬约束不允许通过用户裁决覆盖。

## 6. `FeedbackGovernanceRecord`

`FeedbackGovernanceRecord` 是反馈治理的唯一正式产物，包含：

### 6.1 原始输入

- `recordId`、`version`、`status`、`createdAt`；
- `rawFeedback`、`author`、`targetRefs[]`、`targetVersion`；
- `triggerEvidenceRefs[]`、截图和修改前版本。

### 6.2 专业诊断

- `observedSymptom`；
- `underlyingIntent`；
- `diagnosis`、`rootCause`；
- `domainReviewRuns[]`、`evidenceRefs[]`；
- `overgeneralizationRisk`。

### 6.3 范围与边界

- `feedbackLevel: F0|F1|F2|F3`；
- `scope: element|block|slide|page-family|deck|project`；
- `preserveRefs[]`；
- `counterexamples[]`、`exceptions[]`、`failureConditions[]`。

### 6.4 治理建议

- `aiRecommendation`；
- `alternatives[]`；
- `directExecutionCost`；
- `governedRule`；
- `requiresUserDecision`。

### 6.5 执行与验证

- `userDecision`、`decisionReason`；
- `changeSetRefs[]`；
- `appliedArtifactRefs[]`；
- `professionalReviewRefs[]`；
- `beforeAfterEvidenceRefs[]`；
- `userOutcome: accepted|rejected|continued-feedback|not-evaluated`。

### 6.6 经验资格

- `learningEligibility: eligible|project-only|rejected|pending`；
- `eligibilityReason`；
- `sanitizedMechanism`；
- `applicabilityScope`；
- `experienceRefs[]`。

## 7. 状态机

```text
captured
→ under-review
→ governed
→ needs-user / executable
→ applied
→ professionally-validated
→ user-accepted / rejected
→ learning-eligible / project-only
→ closed
```

任何失败不得覆盖原始反馈、上一有效版本或用户输入。恢复旧版本创建新版本，历史保持不可变。

## 8. 反馈治理 Prompt

```text
稳定反馈治理规则
+ 当前专业场景能力包
+ 当前项目和目标
+ 原始反馈及触发对象
+ 修改前产物和证据
+ 相关优选案例、反例与历史经验
+ 中文角色合同
+ F0–F3 判定规则
+ FeedbackGovernanceRecord 输出合同
= FeedbackGovernanceContextPack
```

稳定 Prompt 必须包含：

> 用户反馈是高价值信号，但不是自动成立的专业结论。先诊断反馈指向的真实问题，再判断其适用范围、反例、代价和更优解决方式。不得为了迎合用户而把局部症状扩大为全局规则。

强制要求：

1. 区分用户观察到的现象和用户提出的解决方式；
2. 可以接受问题判断但否定原解决方式；
3. 检查扩大应用后的反例和失效条件；
4. 调用相关专业标准、优选案例和失败案例对照；
5. 至少提出一个更专业的解决方案；
6. 明确范围、例外和保持不变项；
7. 判定 F0–F3；
8. 只输出诊断、证据、建议和结论，不输出隐藏思维链。

原始反馈只允许进入反馈治理流程及其专业会诊角色。下游生产与审查角色只接收治理后的正式结论。

## 9. 用户交互

### 9.1 反馈治理回执

用户提交反馈后，系统显示：

- 我理解的问题；
- AI 的专业判断；
- 建议如何修改；
- 影响范围与保持不变项。

F0 直接显示修改和复审结果；F1 显示 AI 如何将主观反馈转成专业改进；F2/F3 在执行前显示推荐规则、适用范围、反例、代价和替代方案。

### 9.2 F2/F3 决策面板

只保留三个动作：

- `按 AI 建议修改`；
- `仍按我的原意见执行`；
- `补充说明`。

用户坚持原意见时必须提示：

> 该决定将作为当前项目约束执行，不自动进入跨项目经验。

### 9.3 修改结果回执

显示修改内容、保持不变项、复审范围、前后对比、专业通过状态，并提供：

- `接受本次修改`；
- `继续反馈`；
- `恢复上一版本`。

经验学习状态默认折叠，只在详情显示 `仅当前项目`、`具备候选经验价值`、`已形成候选经验` 或 `已在其他项目验证`。

## 10. Experience Intake 来源

以下来源共同进入经验入口：

- 已治理的项目反馈；
- 用户明确选择的优秀案例；
- 普通参考案例；
- 用户接受的优秀成品；
- 用户否决的失败成品；
- 专业内审失败和工程掉级记录。

来源必须保存项目、版本、目标对象、隐私边界和证据，不允许只保存聊天摘要。

## 11. 三类学习结果

### 11.1 `PreferenceSignal`

记录用户喜欢或不喜欢的表达、审美和内容偏好。用户明确选择的优秀案例和接受成品在偏好层具有较高影响，但偏好不能覆盖专业质量门。

### 11.2 `ProfessionalMechanismCandidate`

记录为什么某种内容、视觉或工程机制有效，必须包含机制陈述、适用场景、条件、证据、反例、失效条件和隐私净化结果。

### 11.3 `AntiPatternCandidate`

记录常见失败、用户否决原因和专业审查失败，例如无语义装饰、截图堆叠、数据无结论、页面机械重复、对齐错误和工程掉级。

一个来源可以形成多条不同类型的学习结果；不得把整套案例作为单一不可拆规则。

## 12. 角色化经验切片

```text
Experience Engine
→ 按场景匹配
→ 按角色过滤
→ 按任务裁剪
→ 标注来源、版本、置信度和范围
→ 形成 Role-specific Experience Slice
→ 注入对应智能体上下文包
```

### 12.1 内容角色

- 售前内容策略专家智能体：决策逻辑、异议、方案边界和说服机制；
- 证据分析智能体：证据强弱、真实素材、过度承诺和证据缺口；
- 叙事架构智能体：论证路径、章节推进、重复和逻辑断裂；
- 内容撰写智能体：专业表达、标题正文、密度和优秀实现；
- 内容审查角色：失败模式、反例、否决原因和已验证质量标准。

### 12.2 视觉与工程角色

- 售前视觉策略专家智能体：听众、行业和决策场景适配；
- 视觉艺术指导智能体：审美机制、视觉张力和整套节奏；
- 编辑设计智能体、信息设计智能体：阅读路径、层级、分区、网格和关系表达；
- 图像艺术指导智能体：摄影、截图、插画和真实性偏好；
- PPT 工程智能体：对齐、字体、裁切、原生可编辑和渲染问题；
- 独立审查角色：什么结果不能通过、常见失败和反例。

生产和审查角色必须使用不同经验切片。独立审查角色不读取生产角色自我评价。

## 13. 专业资格门与偏好择优

### 13.1 第一阶段：专业资格门

所有方案先满足项目事实、用户已确认边界、售前专业要求、最低内容质量、最低审美要求、可读性、可编辑性和 PPT 工程约束。任一适用条件失败即返工。

### 13.2 第二阶段：偏好择优

多个方案均通过专业资格门后，再依据以下信息择优：

1. 用户明确选择的优秀案例；
2. 用户接受的优秀成品；
3. 多次验证的个人偏好；
4. 已验证个人专业经验；
5. 当前项目正向反馈；
6. 普通参考案例和候选经验。

这里的“提高权重”不使用跨质量条件的综合分，而表示优选案例在合格候选之间显著影响最终选择。偏好不能让不合格方案通过。

## 14. 三速进化机制

### 14.1 快速层：当前项目学习

- 已治理反馈可以立即影响当前项目；
- 用户确认偏好进入项目上下文；
- 修改可撤销；
- 不影响其他项目和稳定 Prompt。

### 14.2 中速层：个人经验进化

- 专业复审通过且用户接受后可形成候选经验；
- 在匹配场景中推荐、应用并记录结果；
- 经不同项目真实成功验证后晋级个人经验；
- 个人经验可进入对应角色经验切片；
- 支持禁用、降级、回滚和版本追踪。

### 14.3 慢速层：稳定专业能力进化

- 稳定治理规则、角色合同、场景能力包和 Prompt 模板不得运行时自动修改；
- 只有多项目证据、反例和适用范围稳定后，才进入发布候选；
- 发布前执行正例、反例、跨角色和旧项目回归；
- 独立治理审查通过后发布新版本；
- 质量退化时整体回滚。

## 15. 候选经验资格

只有同时满足以下条件才可形成候选经验：

1. 已存在正式 `FeedbackGovernanceRecord` 或案例分析记录；
2. 机制可以脱离客户专有事实表达；
3. 适用场景、页面任务、条件、反例和失效边界明确；
4. 当前项目修改已通过专业复审；
5. 用户接受了修改结果，或优秀案例经专业分析证明机制成立；
6. 不与事实、安全、质量门和稳定治理冲突；
7. 经验适配审查智能体通过场景匹配检查。

项目特殊决定、未评价修改、错误场景应用和只在测试中模拟成功的记录不得晋级。

## 16. 明确不做

- 不把用户反馈直接作为跨页面或跨项目规则；
- 不把用户喜欢等同于专业普适性；
- 不整体复制优秀案例；
- 不把所有经验原样注入全部智能体；
- 不用偏好补偿事实、内容、审美或工程质量失败；
- 不把错误场景应用计入成功证据；
- 不根据单次反馈或测试模拟自动修改稳定 Prompt；
- 不向用户展示隐藏思维链或内部自由讨论。

## 17. 验收标准

1. 每条反馈都保存原话、目标对象、版本和触发证据。
2. F0–F3 路由、用户介入边界和恢复行为可验证。
3. F2/F3 在扩大执行前显示反例、范围、代价和 AI 推荐。
4. 下游生产角色不直接接收未经治理的用户原话。
5. 项目执行链和经验进化链具有独立状态和版本。
6. 优选案例、参考案例、成功成品和失败成品均可进入 Experience Intake。
7. 偏好信号、专业机制候选和失败模式候选可分别保存和推荐。
8. 经验按角色和任务形成不同切片，生产与审查角色保持隔离。
9. 优选案例只在合格方案中影响择优，不改变质量门。
10. 候选经验应用前强制校验场景、听众、页面任务和条件。
11. 经验应用、评价、晋级、降级、禁用和回滚可追溯。
12. 稳定 Prompt、角色合同和场景能力包不会被运行时自动修改。

## 18. 待验证

- 候选经验晋级所需的真实项目数量；
- 观察周期、自动降级和失效阈值；
- 稳定能力发布前的回归案例规模；
- 各角色经验切片的容量、更新频率和冲突处理；
- F0/F1 自动修复的准确率和用户接受率；
- F2/F3 对用户中断次数和决策负担的影响；
