## 2. 问题与最新决定

当前实现已经具备章节、连续页面、完整字段、真实材料、PageDecision、页内意见、草稿恢复和 ContentReviewBatch 等功能骨架，但首屏被大型状态区、卡片式章节导航、说明型 deck intro 和过大的章节标题占据。用户进入页面后首先感知到的是“审核系统说明”，而不是“开始连续读稿”。

2026-08-18 用户确认：08 原型的精确色值、字体、圆角、阴影、示例客户和示例页内容仍不构成正式跨项目视觉令牌或数据合同；但其空间角色、首屏任务层级、连续阅读节奏、图文同屏关系和 PageDecision 相对位置属于本页实现约束。研发不能再以“具体栅格未冻结”为由更换这些关系。

## 3. 目标与非目标

### 3.1 目标

1. 让用户打开页面后立即进入完整售前稿的连续阅读，而不是先阅读产品说明或工程状态。
2. 恢复 `项目身份/进度 -> 章节定位 -> deck intro -> 章节 -> 第一页正文` 的紧凑节奏。
3. 在桌面参考视口中让第一页实际正文进入首屏。
4. 保留当前所有权威内容、材料、PageDecision、草稿、保存、批次和 revision 语义。
5. 建立结构存在性、空间几何和用户视觉验收三种互不替代的证据。
6. 使本轮变更成为一个可独立 `git revert` 的提交。

### 3.2 非目标

- 不改变 ReadingDeckBlueprint、ContentReviewProjection 或 Runtime 数据合同。
- 不重新设计 PageDecision 业务语义。
- 不修改四类判断、1200 Unicode code points、单页保存或 ContentReviewBatch 规则。
- 不引入产品导航、内容蓝图空间、常驻侧边栏或聊天流。
- 不用示例客户、示例文案或旧页面标题替换当前权威项目数据。
- 不把本地截图、自动化测试或预览地址描述为真实 ReviewSession、宿主打开、AI 接收或用户验收。
- 不在本轮处理视觉专业审核页。

## 4. 方案比较与选择

### 方案 A：只调颜色、字号和间距

优点是改动小、风险低。缺点是无法改变大型状态区、卡片式章节导航和说明型首屏的任务层级；即使视觉更精致，用户仍然要先穿过“页面封面”才能开始读稿。

结论：不采用。

### 方案 B：保留业务组件，结构性还原阅读层级

保留 `ContentFullDeckReviewPage`、`ContentMaterialView`、`PageDecisionControl` 及现有保存/批次逻辑，只重组页头、导航、deck intro、章节头和首屏空间预算。用 08 原型约束相对位置和阅读节奏，用当前权威投影填充内容。

优点是能解决根因，同时不触碰 Runtime 和已验证业务逻辑；变更范围集中，可测试、可回退。缺点是需要新增真实几何验收，不能只依赖 JSDOM 或 selector 测试。

结论：采用。

### 方案 C：逐像素复制 08 原型

优点是视觉差异最小。缺点是会把旧示例数据、旧命名、固定色值和原型一次性实现细节误当成正式产品合同，也难以容纳当前已增强的状态、保存和长文档能力。

结论：不采用。

## 5. 页面结构设计

### 5.1 固定阅读顺序

页面 DOM 和视觉阅读顺序保持：

```text
紧凑项目头与审核进度
-> 细进度轨
-> 单行章节定位条
-> 紧凑 deck intro
-> 章节标题与任务
-> 第一页完整图文正文
-> PageDecision 与页内意见
-> 后续页面和章节
-> 全稿审核收口
```

不得在 deck intro 之前插入新的状态卡、说明卡、产品入口或工程摘要。

### 5.2 紧凑项目头

- 继续显示审核对象、material mode、sourceVersion、revision、已完成/未完成/未保存数量。
- “定位下一页未判断”保留为次操作。
- “完成本轮审核，交给 Codex 集中处理”仍是页面唯一最强主操作。
- 宽视口采用一行紧凑布局；窄视口允许换行，但不能形成三张独立仪表盘卡。
- 进度使用文字和细进度轨共同表达；不只依赖颜色。
- 不新增 Gate、宿主、AI 回执或产品状态卡。

### 5.3 章节定位条

- 章节定位保持单行横向条带，必要时横向滚动，不在宽屏自动换成多行卡片墙。
- 每个章节保持明确可点击边界、章节号、章节名和页范围。
- 现有逐页定位能力可以保留为紧凑数字轨，但不得扩大为整张章节卡。
- 导航只用于定位，不复制正文，不长期占据大块垂直空间。

### 5.4 Deck intro

- deck intro 的角色是“整套稿件阅读导语”，不是审核页功能说明或 hero。
- 使用当前权威内容表达本稿目标、章节/页数、材料模式和关键阅读提示。
- 采用高对比、紧凑的独立区块，使其与普通页面卡形成层级差；精确颜色由当前样式令牌决定。
- 删除或改写“这是连续审核页”一类以解释 UI 为主的冗余文案。
- 不允许 deck intro 的标题、留白或说明文字把第一页正文推出首屏。

### 5.5 章节与页面

- 章节标题恢复为节奏标识，不作为大幅海报标题。
- 章节号、标题、阅读任务、页范围同时存在，但保持紧凑。
- 页面继续使用最终页序连续渲染，正文/材料宽屏双栏、窄屏单栏。
- 完整正文、真实材料、来源、身份、演讲备注、问题—方案映射、跨页关系和阅读质量继续保留。
- PageDecision 紧跟当前页内容，不移动到常驻侧栏或全局操作区。

## 6. 空间合同

空间合同是本阶段的工程验收阈值，不是跨项目永久视觉令牌。以后可以在保持同等首屏任务和阅读效率的前提下调整，但不能只改 selector 名称便宣称保真。

### 6.1 参考视口：1280 × 720 CSS px

- 项目头可视高度不超过 96 CSS px。
- 章节定位条可视高度不超过 64 CSS px。
- deck intro 可视高度不超过 160 CSS px。
- 首屏必须看到第一章标题、第一页标题，并进入第一页实际正文；`.content-slide-reading-grid` 的顶部必须位于首屏底部之上。
- 项目头、章节定位、deck intro、章节头和第一页之间不能出现额外 hero、状态卡墙或大面积空白。
- 页面 `scrollWidth` 不得大于 `clientWidth`。

### 6.2 其他视口

- 1440/1200 CSS px：完整正文与材料保持可读双栏，首屏任务与 1280 基准一致。
- 900/760 CSS px：项目头可以堆叠，正文/材料回落单栏，章节定位仍保持紧凑；不要求第一页正文在 720 高度首屏达到桌面同等深度。
- 480/360 CSS px：无横向溢出；PageDecision 低于 380 CSS px 时为 2×2，单项最小高度 42 CSS px，标签不换行。
- 10、24、60 页均保持最终页序和连续滚动；文本始终完整，远端图片可以近视口加载。

## 7. 组件与数据边界

### 7.1 保留组件

- `ContentFullDeckReviewPage.tsx`：继续负责审核页组合、判断草稿、保存、提交、定位和证据层打开。
- `ContentMaterialView.tsx`：继续负责当前页真实材料和近视口加载。
- `PageDecisionControl.tsx`：继续负责四选一、意见、保存和可访问性。
- `content-review.css`：承担本轮主要布局和层级还原。

### 7.2 不新增第二套状态

本轮不在 React 中推断章节、sourceVersion、revision、完成状态或材料身份，不新增页面私有业务状态。所有业务事实继续来自现有投影和现有 draft/store 边界。

### 7.3 允许的小范围结构调整

可以为几何验收增加稳定语义标识，例如：

- `data-content-review-header`
- `data-content-review-progress-track`
- `data-content-review-chapter-nav`
- `data-content-review-deck-intro`
- `data-content-review-first-reading-grid`

这些标识只用于可访问性、测试和验收，不形成新的业务对象。

## 8. 错误、保存与恢复

本轮不改变错误语义：

- projection 无效时继续只读并提示刷新；
- revision/source 冲突保留本地输入；
- 单页保存失败保留选择和意见；
- 批次提交失败保留全部输入；
- 证据层关闭后恢复原页面位置和触发焦点；
- 未完成页、未保存意见或活动保存存在时，批次主操作保持禁用。

布局还原不得通过删除状态、隐藏错误或减少正文来取得首屏空间。

## 9. 测试与验收设计

### 9.1 TDD 顺序

1. 先增加会失败的空间合同测试和 DOM 语义测试。
2. 运行定向测试，确认失败原因是当前标题/导航/deck intro 过高或缺少几何合同，而不是测试错误。
3. 最小化修改 DOM/CSS 使测试通过。
4. 运行内容页定向测试、全量 Widget 测试、typecheck 和 build。
5. 在同一 `1280 × 720` 视口渲染 08 原型与当前实现，生成首屏和 PageDecision 交互截图。
6. 由用户进行独立 UI fidelity 验收；自动化通过不能替代该结果。

### 9.2 自动化分层

| 层次 | 检查内容 | 不能证明 |
|---|---|---|
| 单元/DOM | 结构顺序、完整字段、PageDecision 行为、草稿与批次 | 真实布局和视觉层级 |
| 响应式源码契约 | 42px、2×2、双栏/单栏、无已知溢出规则 | 浏览器实际 bounding box |
| 浏览器几何 | 1280×720 的高度预算、首屏正文、无横向溢出 | 用户视觉认可 |
| 截图对照 | 原型与实现的首屏/交互差异 | 真实宿主与 AI 回执 |
| 用户验收 | 是否满足已确认 UI | Runtime/宿主真实性 |

### 9.3 必须保留的回归

- 四类 PageDecision 互斥；
- 非 approved 意见必填且最多 1200 Unicode code points；
- 42 CSS px 与 380 CSS px 以下 2×2；
- 60 页连续 DOM 顺序；
- 当前页真实材料可加载或有确定性重试；
- 证据层焦点与滚动恢复；
- 单页保存不触发 Codex、不改稿、不确认 G0；
- 全页完成前不能提交批次；
- 不出现五空间、产品导航、常驻侧边栏或聊天记录。

## 10. 版本与回退

- 设计规格和基线澄清先形成独立文档提交。
- 用户确认书面规格后，再形成一个“内容审核页空间还原”实现提交。
- 实现提交只允许修改内容审核页组件、样式、相关测试和本阶段验收脚本/记录。
- 视觉页、Runtime 和宿主回执不得混入该提交。
- 验收不通过时使用 `git revert <content-review-spatial-restore-commit>` 回退，不重写共享历史。

## 11. 阶段出口

以下全部满足才可称“内容审核页实现完成，等待用户验收”：

1. 结构、定向测试、全量 Widget 测试、typecheck 和 build 通过；
2. 1280×720 浏览器几何合同通过；
3. 360、760、1000、1280、1440 CSS px 无横向溢出；
4. 原型和实现的同视口首屏/交互截图已经生成；
5. 验收记录明确区分自动化、本地 Browser、真实宿主和用户验收；
6. 工作树只包含本阶段文件；
7. 用户视觉验收状态仍显示 `pending`，直到用户明确接受。

只有用户明确接受后，才可以把本页标记为 `UI fidelity accepted` 并进入视觉审核页阶段。

## 12. 规格自审

- 未发现未决占位项或缺失章节。
- 第一轮范围只包含内容全稿审核页。
- 空间合同与“精确视觉令牌不冻结”不冲突：前者约束当前页面任务和几何验收，后者允许未来在保持同等关系时调整具体表达。
- 不修改 Runtime、ReviewSession、宿主通知或 AI 接收合同。
- 自动化、本地截图、真实宿主和用户验收的证据边界相互独立。
- 设计保留当前已经验证的业务功能，不通过删内容或隐藏状态换取视觉相似。
