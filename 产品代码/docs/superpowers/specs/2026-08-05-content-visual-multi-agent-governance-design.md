## 1. 目标

建立一套覆盖内容、视觉、工程、反馈和学习的受治理多智能体生产体系。系统不能依赖单一模型一次生成，也不能用更多角色数量代替明确职责、结构产物、独立审查和质量门。

AI 是主要生产者。用户负责提供任务、材料、关键判断、反馈和最终验收；系统负责编排角色、隔离上下文、保存产物、执行质量门、控制版本并治理经验进化。

## 2. 核心原则

1. 内容先于视觉：G0 未通过前不得形成正式视觉结论。
2. 生产与审查隔离：同一智能体不能生产并放行自己的结果。
3. 结构产物协作：智能体之间通过不可变、版本化产物协作，不通过自由群聊传递决定。
4. 场景专家化：通用治理内核与阅读优先售前场景能力包分离。
5. Prompt 版本化：稳定治理、场景能力、角色合同、任务合同、工具任务和返工要求均有版本。
6. 二元质量门：适用硬条件只允许 `通过 / 未通过 / 不适用`，任一失败即返工。
7. 用户只处理高影响事项：内部初稿、候选争论和自动返工不转化为用户待办。
8. 反馈先治理：用户原话是高价值信号，不自动成为专业规则。
9. 案例先提炼：优秀案例和失败案例必须提炼机制、范围、证据和反例，不能整套复制。
10. 经验按角色注入：生产、审查、返工和治理智能体接收不同的经验切片。
11. 稳定能力慢速发布：运行时经验不得自动修改稳定 Prompt、角色合同或场景能力包。
12. 不保存隐藏思维链：只保存角色、输入版本、外化结论、证据、失败项、返工和通过记录。
13. 正式生产采用严格路线 B：视觉合同先形成，Presentations 同时承担原生视觉设计和 PPTX 实现，Image 2 只在原生首版后生成非语义资产。
14. 目标 PowerPoint 是渲染真相源：开发渲染只作预检，G2/G4 必须保存目标软件实机证据。

## 3. 中文命名规范

产品文档、Prompt 合同和用户界面中的正式角色名称统一使用中文，格式为：

```text
专业领域 + 职责 + 智能体
```

示例：`售前内容策略专家智能体`、`独立审美审查智能体`、`反馈治理编排智能体`。

代码和 Schema 可以保留稳定英文 `roleId`，但不得把英文标识直接作为用户可见名称。产品名称中的“Agent 原生工作台”和既有对象名 `AgentTask` 属于兼容性术语，不代表角色名称继续使用英文。

## 4. 总体架构

```text
任务书与材料
→ 内容生产团队
→ 内容独立审查团队
→ G0 用户确认
→ 视觉设计团队
→ 视觉独立审查团队
→ Presentations 原生锚点页
→ 可选 Image 2 非语义资产
→ 目标 PowerPoint 实机审查
→ G1/G2 内部通过
→ G3 用户确认
→ Presentations 整套原生生产
→ 开发预检 + 目标 PowerPoint 整套实机审查
→ G4 用户验收

反馈治理编排智能体贯穿 G0、G3、G4
经验进化治理智能体向各角色提供版本化经验切片
```

反馈治理和经验进化是横向能力，不取代内容、视觉或工程专业审查，也不改变 G0–G4 的既有门定义。

## 5. 内容阶段

### 5.1 生产团队

- 内容生产编排智能体；
- 售前内容策略专家智能体；
- 证据分析智能体；
- 叙事架构智能体；
- 内容撰写智能体。

### 5.2 审查团队

- 售前专业审查智能体；
- 决策者视角审查智能体；
- 证据审查智能体；
- 叙事审查智能体；
- 专业表达审查智能体；
- 独立总编智能体。

### 5.3 主要产物

`PresalesContentStrategy`、`ClaimEvidenceMap`、`DeckArgumentMap`、`SlideDraftSet`、`ContentReviewRecord`、`ContentRepairPlan`、`ContentAcceptanceRecord`、`ContentBlueprint`。

具体职责、状态机和内容质量合同以内容生产专项设计为准。

## 6. 视觉阶段

### 6.1 固定生产团队

- 视觉设计编排智能体；
- 售前视觉策略专家智能体；
- 视觉艺术指导智能体；
- 编辑设计智能体；
- 信息设计智能体；
- 图像艺术指导智能体；
- PPT 工程智能体。

### 6.2 动态页面专家

按实际内容路由，例如：

- 案例页设计专家智能体；
- 架构图设计专家智能体；
- 数据可视化专家智能体；
- 复杂流程设计专家智能体。

动态专家只在对应页面家族或内容风险出现时运行，不成为固定常驻角色。

### 6.3 独立审查团队

- 售前视觉适配审查智能体；
- 独立审美审查智能体；
- 信息表达审查智能体；
- 编辑阅读审查智能体；
- PPT 工程审查智能体。

### 6.4 主要产物

`VisualBrief`、`CreativeDeliberationRecord`、`DeckDesignSystem`、`SlideVisualContract`、`AnchorSlideSet`、`AestheticAcceptanceRecord`、`VisualContract`、`SlideSceneGraph`。

具体协作流程、Prompt、工具任务包和视觉质量合同以视觉设计专项为准。

## 7. 反馈与经验治理

### 7.1 治理角色

- 反馈治理编排智能体；
- 反馈反例审查智能体；
- 经验提炼智能体；
- 经验适配审查智能体；
- 经验进化治理智能体。

反馈治理编排智能体根据反馈对象调用内容、视觉或工程专业智能体会诊，但不替专业角色决定内容或视觉结果。

### 7.2 正式输入与输出

```text
RawFeedback
→ FeedbackGovernanceRecord
→ ContentChangeSet / VisualChangeSet
→ 应用与专业复审
→ 用户结果评价
→ Experience Intake
```

原始反馈只进入反馈治理流程。下游生产与审查角色默认接收治理后的结论；原话如需保留，只能作为可追溯引用，不能作为未经解释的强制指令。

## 8. Prompt 与 Context Pack 总结构

### 8.1 内容角色

```text
稳定治理层
+ 售前内容场景能力包
+ 当前项目事实
+ 中文角色合同
+ 当前任务合同
+ 角色化经验切片
+ 返工要求（按需）
= 内容角色上下文包
```

### 8.2 视觉角色

```text
稳定视觉治理
+ 售前视觉场景能力包
+ 当前项目与 G0 内容
+ 中文角色合同
+ 当前任务与工具合同
+ 角色化经验切片
+ 审查返工要求（按需）
= VisualAgentContextPack
```

### 8.3 反馈治理角色

```text
稳定反馈治理规则
+ 当前专业场景能力包
+ 当前项目和目标
+ 原始反馈及触发对象
+ 修改前产物和证据
+ 优选案例、反例与历史经验
+ 中文角色合同
+ F0–F3 判定规则
+ FeedbackGovernanceRecord 输出合同
= FeedbackGovernanceContextPack
```

## 9. 协作与隔离

1. 生产智能体只读取完成当前任务所需的上游产物，不读取审查结论或其他生产角色的自我评价。
2. 审查智能体不读取生产角色自我评价；独立审查之间默认互不可见。
3. 编排智能体只负责版本、依赖、路由、状态和产物完整性，不越权替专业角色生产或放行。
4. 独立总编智能体和对应阶段的审查聚合角色可以读取各自阶段全部失败记录，用于去重和返工路由。
5. 返工任务必须声明目标范围、保持不变项、失败条件、所需结果和复验路线。
6. 反馈治理角色可以看到用户原话，但必须将其标记为待评审假设。
7. 每次运行保存治理版本、场景版本、角色版本、任务版本、经验版本和输入产物版本。

## 10. 用户介入边界

用户正式检查点保持：

- G0 内容确认；
- G3 整套视觉合同确认；
- G4 最终成稿验收。

智能体只在以下例外中断用户：

- 关键事实或权威来源冲突；
- 核心证据或素材缺失；
- 任务、听众、方案边界或商业承诺存在真实歧义；
- 用户反馈与专业最低质量或已确认边界发生高影响冲突；
- 可编辑性与设计意图无法自动裁决；
- 在待真实项目验证的系统限制内无法收敛。

内部候选方案、审查分歧、普通返工和过程版本不得转化为大量用户待办。

## 11. 质量门与参考偏离

内容、视觉和工程规则统一分为：

- `必须严格遵守`；
- `最低内容质量` 或 `最低审美要求`；
- `参考实现`。

前两类任一适用条件失败即返工。参考实现可以被更优秀方案替代，但必须由对应独立审查角色证明没有破坏硬条件，并保存偏离理由和证据。禁止数字评分、加权平均、多数投票和跨条件补偿。

## 12. 经验使用原则

1. 经验按场景匹配、角色过滤和任务裁剪后形成 `Role-specific Experience Slice`。
2. 生产角色重点接收成功机制和用户偏好；审查角色重点接收失败模式、反例和质量边界。
3. 候选经验只能作为建议和检查线索，不能成为硬规则。
4. 已验证个人经验可以提高择优影响，但仍不能覆盖项目事实和专业质量门。
5. 每次经验应用必须记录版本、匹配理由、目标项目、结果和用户评价。
6. 经验支持禁用、降级、回滚和版本化。

## 13. 明确不做

- 不向用户展示隐藏思维链或内部自由讨论；
- 不为每个角色建立独立用户确认门；
- 不让同一角色同时生产并放行自己的结果；
- 不把所有经验原样注入所有角色；
- 不把用户反馈、优秀案例或失败案例直接改写为稳定规则；
- 不用角色数量、评分或表面流程复杂度证明质量；
- 不绕过严格路线 B：不得用 Image 2 整页结果指挥正式 Presentations 复刻，不得用开发渲染替代目标 PowerPoint 实机证据。

## 14. 验收标准

1. 内容和视觉阶段均存在正式生产团队、独立审查团队、结构产物和二元质量门。
2. 所有用户可见角色名称为中文，机器标识不直接暴露。
3. 内容智能体不能提前形成视觉结论，视觉智能体只能使用已通过 G0 的内容版本。
4. 生产角色不能自我放行，审查角色的失败能生成定向返工任务。
5. 用户首次看到的内容和视觉版本均已通过对应内部质量门。
6. 用户反馈先形成 `FeedbackGovernanceRecord`，再形成修改集。
7. 优选案例只在通过专业资格门的候选中影响择优，不补偿质量失败。
8. 经验按角色注入并记录应用结果，稳定能力不会被运行时静默修改。
9. G0、G3、G4 以外不新增常规用户确认门。
10. 全流程不保存或展示隐藏思维链。
11. 正式项目固定严格路线 B；Image 2 只在原生首版后生成非语义资产，A/C 实验与正式项目隔离。
12. G2 锚点页和 G4 整套均有当前生产平台 PowerPoint 实机证据，并通过业务语义、视觉完成度、排版工程和目标渲染四门。

## 15. 待验证

- 各阶段实际并行数量、返工轮次、耗时与成本限制；
- 动态页面专家的路由准确性；
- 生产与审查经验切片的最优容量和更新频率；
- 多智能体结果的一致性、盲点与重复劳动；
- 反馈治理和视觉创意的自动收敛边界；
- 真实项目中的用户中断次数和首次可审版本接受率。

以上阈值必须通过真实售前项目验证，研发不得自行固定。
