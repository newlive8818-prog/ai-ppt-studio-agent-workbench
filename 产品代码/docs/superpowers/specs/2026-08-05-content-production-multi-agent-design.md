# AI PPT Studio 内容生产多智能体架构设计

> **文档身份：历史，已废止。** 2026-08-14 起，固定内容多智能体、观点先行对象和五类固定审查不再是产品合同。当前权威设计见 [售前方案总师 Agent、证据先行内容生产与双层经验设计](./2026-08-14-presales-chief-agent-content-and-experience-design.md)。本文件只用于迁移和追溯，不得用于创建新实现计划。

**日期：** 2026-08-05

**状态：** 历史，已废止；不得据此创建新实现

**适用范围：** 一期阅读优先的售前解决方案汇报，内容蓝图形成、内部审查、用户修改与 G0 冻结

**权威输入：** 项目根目录四份唯一研发基线；发生冲突时以更新后的产品需求基线为准

## 1. 目标

将内容蓝图从“单一智能体一次生成、用户直接审阅”的结果升级为受治理的多智能体内容生产系统。AI 在用户首次审阅前完成专业策划、证据绑定、整套叙事、逐页写作、独立审查和定向返工；用户只处理真实业务歧义、高影响决定和最终 G0 确认。

用户看到的第一版必须已经通过内部内容质量合同。内部初稿、审查失败稿和返工稿默认不作为用户待审版本，但保留为可追溯过程版本。

## 2. 已确认产品原则

1. 内容阶段采用正式的多智能体生产与独立审查架构。
2. 生产角色与审查角色隔离，同一生成角色不得自我声明通过。
3. 首次内部初版必须经过全量多智能体审查；任一适用硬条件失败即定向返工。
4. 高影响修改执行全量重审；普通修改按影响范围复审，但不得豁免适用硬条件。
5. 智能体之间不以自由群聊传递决定，只通过版本化结构产物协作。
6. 采用“通用内容内核 + 版本化场景专家能力包”；一期配置“阅读优先售前解决方案”能力包。
7. 生产侧与审查侧售前专家使用同一专业内核，但使用不同角色合同和隔离上下文。
8. 用户默认不查看内部未通过版本；可主动进入过程版本，但过程版本不得用于 G0。
9. AI 默认自动返工；只有真实业务歧义、关键证据缺失或系统无法收敛时才中断用户。
10. 用户意见先形成 `FeedbackGovernanceRecord`，再生成 `ContentChangeSet` 并按影响范围重新生产和复审。
11. 单次反馈只形成项目治理记录；只有经过专业复审、用户结果评价和适用范围提炼后才可能形成候选经验，不直接修改稳定治理层或售前专家能力包。

## 3. 角色与职责

| 角色 | 主要职责 | 不承担 |
|---|---|---|
| 内容生产编排智能体 | 编译任务上下文、调度角色、维护依赖、版本和状态 | 不写正文，不替审查角色放行 |
| 售前内容策略专家智能体 | 判断听众、决策阶段、核心矛盾、异议、说服命题和证据要求 | 不伪造客户事实，不直接冻结 G0 |
| 证据分析智能体 | 建立事实、推断、建议、来源、冲突、缺口和主张证据关系 | 不用行业常识替代项目证据 |
| 叙事架构智能体 | 建立整套论证地图、章节任务、页面角色、推进关系和节奏 | 不提前决定颜色、版式和视觉风格 |
| 内容撰写智能体 | 根据已通过策略、证据和结构形成完整可见文案与讲解稿 | 不改变上游目标、事实和方案边界 |
| 售前专业审查智能体 | 判断是否真正推动当前售前决策、是否回应关键角色疑虑 | 不读取生产侧自我评价，不直接改稿 |
| 决策者视角审查智能体 | 从主要决策者认知起点检查必要性、价值、风险和下一步 | 不用个人偏好替代任务书 |
| 证据审查智能体 | 检查事实身份、来源强度、过度承诺、证据缺口和冲突 | 不直接补造缺失事实 |
| 叙事审查智能体 | 检查整套逻辑、重复、跳跃、章节推进和页面必要性 | 不直接重排或改写内容 |
| 专业表达审查智能体 | 检查标题、正文、讲解稿、阅读独立性、专业度和 AI 腔 | 不改变已确认事实和主张 |
| 独立总编智能体 | 聚合隔离审查、消歧、生成返工计划或内部通过记录 | 不亲自替生产角色修改正文 |

以上是任务级角色运行，不要求每个角色对应常驻进程。代码可保留英文 `roleId`，产品文档、Prompt 合同和用户界面只显示中文正式名称。运行时可并行调度相互独立的审查，但必须保持角色输入、输出和证据隔离。

## 4. 场景专家能力包

一期 `PresalesSolutionScenarioPack` 至少包含：

- 售前任务模型和客户决策链；
- 决策者、业务负责人、技术评审者、影响者和潜在否决者的关注差异；
- 建设必要性、方案边界、实施路径、风险、价值和案例证据的专业论证关系；
- 常见客户异议、证据偏好、过度承诺风险和禁用表达；
- 阅读优先售前方案的内容质量标准；
- 场景专属诊断问题、审查规则、参考实现和反例；
- 能力包版本、适用范围、变更理由和回归测试记录。

场景能力包提供专业判断和检查方法，不强制所有项目采用固定章节模板，不得覆盖用户事实、任务书和已确认决定。

## 5. 分层提示与 Context Pack

每次智能体运行由 Context Compiler 组合：

```text
稳定治理层
+ 场景专家层
+ 项目事实层
+ 当前角色层
+ 当前任务层
+ 角色化经验切片
+ 返工要求层（仅返工时）
= Role-specific Context Pack
```

规则：

1. 稳定治理层规定事实边界、来源、版本、用户优先级、输出合同和审查隔离。
2. 场景专家层只提供当前专业场景所需的方法、风险和质量规则。
3. 项目事实层只来自用户材料、任务书、已确认事实和决定。
4. 角色层限制本次智能体的职责、可写产物和禁止动作。
5. 任务层声明输入版本、目标引用、影响范围、输出 Schema 和验收条件。
6. 返工层只包含失败条件、目标范围、修复结果和上一有效版本。
7. 审查智能体不接收生产智能体的自我评价，也不提前接收其他审查记录。
8. 每个 Context Pack 保存所用治理、场景、角色、任务和经验版本，以支持复现。
9. 用户原始反馈只进入反馈治理流程；内容角色只接收治理后的反馈结论、保持不变项和执行范围。

## 6. 正式中间产物

| 产物 | 核心内容 | 主生产者 |
|---|---|---|
| `PresalesContentStrategy` | 决策阶段、听众、核心矛盾、异议、说服命题、边界和证据要求 | 售前内容策略专家智能体 |
| `ClaimEvidenceMap` | 主张、事实、推断、建议、来源、证据强度、冲突和缺口 | 证据分析智能体 |
| `DeckArgumentMap` | 章节任务、页面角色、核心主张、推进关系和整套节奏 | 叙事架构智能体 |
| `SlideDraftSet` | 每页完整标题、可见文案、讲解稿、来源、材料和内容状态 | 内容撰写智能体 |
| `ContentReviewRecord` | 审查角色、条件、适用性、通过/未通过、证据和返工指令 | 各独立审查智能体 |
| `ContentRepairPlan` | 去重后的失败项、责任角色、目标范围、保持不变项和复验路由 | 独立总编智能体 |
| `ContentAcceptanceRecord` | 全部适用条件、内部通过结果、证据、偏离理由和版本 | 独立总编智能体 |
| `FeedbackGovernanceRecord` | 用户原话、专业诊断、范围、反例、AI 建议、用户决定和经验资格 | 反馈治理编排智能体 + 专业会诊角色 |
| `ContentChangeSet` | 治理后的修改意图、影响范围、保持不变项和重审路由 | 系统依据治理记录生成 |

智能体不得静默修改其他角色的产物。修订创建新版本并保留被替代关系；用户决定和真实材料始终高于智能体产物。

## 7. 内容生产状态机

```text
strategy-building
-> evidence-mapping
-> narrative-structuring
-> slide-drafting
-> multi-agent-review
-> repairing
-> re-reviewing
-> internally-passed
-> user-reviewable
-> G0 passed
```

异常分支：

```text
任一生产或审查阶段
-> needs-user / partial / failed / cancelled
-> 用户决定、重试或恢复
-> 返回受影响阶段
```

失败不得清空上一份有效版本。内部未通过版本可以保存和查看，但不得标记为 `user-reviewable` 或用于 G0。

## 8. 三层内容质量合同

### 8.1 必须严格遵守

- 与任务书、主要听众和期望决策一致；
- 关键事实、数字、案例、能力和承诺可追溯；
- 来源事实、来源推断和 AI 补充表达身份清楚；
- 不伪造客户现状、产品能力、案例效果或实施承诺；
- 每页只有一个可复述的核心主张、清晰任务和存在必要性；
- 章节和页面不存在事实或逻辑矛盾；
- 缺失证据不得被模糊措辞掩盖；
- 不改变用户已冻结内容和明确禁止项；
- G0 前不形成配色、布局和视觉审美结论。

### 8.2 最低内容质量

- 明显体现对当前客户、行业、项目材料和决策阶段的理解；
- 整套内容形成完整说服路径，不是材料、功能或公司介绍的拼接；
- 章节之间具有因果、递进、比较或决策关系；
- 没有重复页、空泛页和仅起装饰作用的页面；
- 回应关键听众的反对意见、风险和实施疑虑；
- 标题表达判断或结论，而不只是主题名称；
- 正文专业、具体、克制，不出现明显套话和 AI 腔；
- 阅读者不听讲解也能理解主要结论；
- 讲解稿补充背景和推理，不机械复述页面；
- 内容密度合理，超载页面会被拆分或重构；
- 结尾形成明确的期望判断、行动或下一步。

### 8.3 参考实现

- 推荐页数和章节数量；
- 常见的“问题—方案—价值—实施”顺序；
- 标题句式、正文组织方式和讲解稿长度；
- 决策层、推理层和验证层的具体分布。

`must-follow` 与 `minimum-content-quality` 任一适用条件失败即返工。`reference-implementation` 可以被更优秀的实现替代，但审查记录必须证明新实现更适合当前听众、目标和证据。禁止数字评分、加权平均、多数投票和优点补偿。

## 9. 审查、返工与收敛

1. 首次内部初版运行全部审查角色。
2. 审查角色独立输出，不先读取其他审查意见。
3. 独立总编去重、识别冲突并将失败项路由给对应生产角色。
4. 审查角色只诊断，不直接改稿；生产角色只修改被授权的目标范围。
5. 修复后由原审查角色复验，并至少补做一次整套连贯性检查。
6. 局部表达修改只运行表达审查和受影响页检查；局部内容修改增加售前、证据和上下游检查；结构性或高影响修改执行全量重审。
7. 所有问题具有唯一 ID、失败证据、违反规则、影响范围、责任角色、目标结果和复验状态。
8. 任一适用硬条件未通过时，`ContentAcceptanceRecord.overallResult` 必须为 `failed`。
9. 表达偏好冲突由独立总编依据听众、目标和证据裁决，不采用多数票。

## 10. 人工暂停

只在以下条件暂停：

- 权威材料之间存在关键事实冲突；
- 核心主张依赖的事实或材料缺失；
- 听众、目标、方案边界或商业承诺存在真实歧义；
- 场景专业判断与用户明确意图冲突；
- 分支会实质改变页数、方案范围或决策主线；
- 多轮修复仍反复违反同一硬条件；
- 达到待真实项目验证的轮次、耗时或成本限制。

系统一次只向用户提出一个最高影响问题，说明原因、影响范围、AI 推荐、2–3 个互斥处理方式和恢复路径。用户决定后恢复受影响生产链，不要求用户接管整套半成品。

## 11. 用户审阅与反馈

内部通过后，内容蓝图提供：

1. `整套结构审阅`：核心命题、说服路径、章节任务、逐页主张、页面关系和证据覆盖；
2. `完整内容审阅`：连续展示每页标题、全部可见文案、讲解稿、事实身份、来源、材料和未决项；
3. 区块级批注、整套修改意见、版本比较和 G0 集中确认；
4. 过程版本入口，默认折叠内部失败稿并标记“不可用于 G0”；
5. 内部审查通过状态、自动修复摘要、仍需用户判断的问题和影响范围。

用户反馈先形成 `FeedbackGovernanceRecord`。AI 必须诊断真实问题、检查反例和适用范围、提出比原始解决方式更专业的建议；F2/F3 反馈由用户裁决后再生成 `ContentChangeSet`。`ContentChangeSet` 必须解释改什么、哪些保持不变、影响哪些页面、需要重跑哪些智能体。新版重新通过适用审查后才返回 G0 审阅。

## 12. 经验治理

- 用户反馈先成为项目级原始记录，经过治理后才成为修订依据；
- 专业复审通过且用户接受结果后，治理记录才可能形成带场景、原因、证据、适用范围和反例的候选经验；
- 候选经验必须经过不同项目的成功应用和评价后才能晋级；
- 单次反馈不得直接修改稳定治理层、角色合同或场景专家能力包；
- 已晋级经验可以查看、禁用、回滚和版本化。
- 内容生产和内容审查角色使用不同的角色化经验切片；失败模式优先进入审查和返工角色。

## 13. 明确不做

- 不新增用户逐智能体确认或逐页强制确认；
- 不展示内部智能体对话或隐藏思维链；
- 不用更多智能体数量代替角色隔离、结构产物和质量合同；
- 不把场景专家能力包变成固定章节模板；
- 不允许行业常识覆盖项目事实；
- 不在本次设计中预设内部轮次、耗时和成本阈值；
- 不在本次写入中实现代码、Schema、MCP 工具或 Widget 页面。

## 14. 验收标准

1. 用户首次看到的内容蓝图已有 `ContentAcceptanceRecord` 且全部适用硬条件通过。
2. 生产侧和审查侧售前专家使用隔离上下文，审查侧不读取生产侧自评。
3. 每个关键主张可定位到证据、推断身份或明确缺口。
4. 任一审查失败能定位到具体范围并生成可执行返工任务。
5. 修复只修改目标范围，未受影响内容保持，整套连贯性重新检查。
6. 用户可查看结构审阅、完整内容审阅、区块批注、版本差异和过程版本。
7. 内部未通过版本不能通过 G0。
8. 用户反馈先形成 `FeedbackGovernanceRecord`，再生成 `ContentChangeSet`；修改后按风险执行局部或全量复审。
9. 关键证据缺失、事实冲突和无法收敛能进入 `needs-user`，上一有效版本不丢失。
10. 单次反馈不会直接成为候选经验，也不会修改场景能力包或稳定内核。

## 15. 待验证

- 首次全量审查和局部复审的实际智能体运行数量；
- 内部返工最大轮次、时间和成本限制；
- 不同页数、材料量和项目复杂度的最优并行策略；
- 售前专家生产与审查的一致性、盲点和跨项目稳定性；
- 内容质量合同中“最低内容质量”的可重复判定证据；
- 候选场景经验的晋级样本数量和评价方式。

这些阈值必须通过真实售前项目记录后另行确认，研发不得自行填写固定数值。
