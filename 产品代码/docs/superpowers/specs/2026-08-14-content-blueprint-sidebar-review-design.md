## 2. 设计结论

内容蓝图阶段采用三层、两次明确授权的渐进流程：

1. **任务书与目录框架先在 Codex 对话中讨论。** 目录未确认前，不生成、也不展示任何逐页内容。
2. **用户明确允许展开全部页面后，AI 一次性生成内部通过的完整逐页内容蓝图。** 该授权只启动完整全稿规划，不是 G0。
3. **最大宽度侧边栏连续承载整套全稿审核。** 用户从第一页连续读到最后一页，逐页判断并保存意见；全部页面判断完成后，才能提交一个冻结的审核批次。
4. **Codex 先提出整体修改方案。** 用户确认修改方案后，AI 才生成新的完整内容版本；新版本重新进入全稿审核。
5. **最终版本通过审核后，用户再在 Codex 对话中正式确认 G0。** G0 前不讨论页面布局、配色、视觉风格或 PPTX 实现。

核心产品决定是：**内容蓝图的完整正文审核从 Browser 主表面迁入最大宽度 Codex 侧边栏；Browser 降为可选材料放大、原始文件查看、并排比较和跨页关系辅助。** 视觉合同 G3 仍沿用 Codex 内置 Browser 专业审阅，不在本次范围内迁移。

## 3. 要解决的问题

### 3.1 现有流程的问题

- 目录、逐页规划、材料和审核状态同时出现，用户在总体结构尚未稳定时被迫处理页面细节。
- 侧边栏只投影状态和入口，内容本体仍在 Browser，不能发挥与 Codex 对话并行阅读的优势。
- 逐页信息散落为摘要、字段或文字说明，用户不能一眼看到页面目标、实际文案、真实材料和逐字稿之间是否一致。
- 图片材料只被文字描述而未直接举证，用户无法判断案例的哪一页、哪一块内容真正支撑了主张。
- 保存零散标记后即进入反馈治理，缺少“先完整审完一轮、再集中处理”的稳定批次。

### 3.2 成功标准

- 用户先只判断整套讲解框架是否成立，不被未授权的逐页细节干扰。
- 侧边栏明显优于阅读 Markdown：信息结构更稳定，全文、图片材料、来源和审核动作同屏可见。
- 用户不打开逐字稿也能独立理解每一页；逐字稿只补充讲法，不替页面承担核心信息。
- 用户能连续审完全部页面、快速定位未判断页，并形成一个完整、版本绑定的修改批次。
- Codex 能根据整批意见做跨页、跨章节分析，先解释修改方案，避免逐条机械修改造成结构漂移。

## 4. 三个工作表面的新分工

| 表面 | 内容蓝图阶段核心职责 | 不承担 |
|---|---|---|
| Codex 对话 | 任务书、目录框架反复讨论；复杂反馈；阶段授权；批次修改方案确认；最终 G0 | 长篇全稿的主要阅读面；每保存一条就自动改稿 |
| Codex 最大宽度侧边栏 | 完整、连续、图文结合的全稿阅读；逐页判断；意见保存；批次完成校验与提交 | 目录未确认前提前展示逐页内容；自动确认 G0；视觉设计和 PPT 编辑 |
| Codex 内置 Browser | 可选放大原始材料、查看源文件、并排比较案例/页面、检查跨页关系；继续承担 G3 视觉合同审阅 | 内容蓝图完整审核的唯一入口；把侧边栏内容降成摘要 |

侧边栏与 Browser 都只是权威项目对象的投影，不保存第二份业务真相。用户在侧边栏保存的审核判断和意见必须通过 Python 权威运行时持久化。

## 5. 阶段状态机

```text
MissionConfirmation 已就绪
  → framework-discussion
  → AI 生成目录框架草案
  → 用户与 Codex 反复讨论
  → framework-confirmed
  → 用户明确“允许展开全部页面”
  → AI 生成策略、证据、论证、完整逐页内容
  → 隔离内容审查与自动返工
  → ContentAcceptanceRecord passed
  → full-deck-review-ready
  → 用户在侧边栏连续审核全部页面
  → 29/29 页 completed，且无未保存意见
  → ReviewBatch submitted/frozen
  → Codex 生成整体修改方案
  → 用户在 Codex 确认修改方案
  → AI 生成新 ContentBlueprint 版本并复审
  → 新版本重新进入 full-deck-review-ready
  → 最终版本审核完成
  → 用户在 Codex 明确确认 G0
  → 才允许进入视觉构想
```

### 5.1 框架确认不是新 Gate

`framework-confirmed` 和“允许展开全部页面”都是 G0 内部阶段状态，不新增 G 编号：

- 框架确认：允许 AI 基于当前目录生成整套逐页规划；
- 全稿审核完成：允许提交本轮意见给 Codex 集中治理；
- 修改方案确认：允许 AI 应用本批次修改并生成新版本；
- G0：用户对最终完整全稿的正式内容冻结。

这些动作不可互相替代，也不能复用同一个用户消息作为多个凭据。

### 5.2 框架未确认时的侧边栏

侧边栏只展示：

- 当前任务书摘要；
- 核心命题与说服路径；
- 章节目录、每章任务、预期推进关系；
- AI 识别的结构风险和一个最高影响待讨论问题；
- 当前状态 `目录框架讨论中`。

禁止展示逐页标题、页面文案、图片材料计划、逐字稿或逐页审核按钮。复杂讨论继续留在 Codex 对话。

## 6. 完整内容质量合同

### 6.1 “页面实际文字”必须是全文

侧边栏中的“页面实际文字”必须逐字展示计划放进 PPT 页面的全部可见文字，包括标题、副标题、分组标题、正文、图表/流程标签、数据说明、脚注和必要来源标注。禁止：

- 用 AI 摘要代替实际页面文字；
- 只显示几个能力标签或抽象关键词；
- 省略号、行数截断、hover 才显示全文；
- 把核心论证藏入逐字稿；
- 以图片预览存在为由不提供可检索的文字投影。

### 6.2 阅读优先的最低结果

每页必须形成可独立阅读的闭环：

1. 一个结论型主张；
2. 解释该主张为何成立的必要理由；
3. 真实证据、可核验材料或明确的证据身份/缺口；
4. 适用范围、方案边界或待联合验证项；
5. 与前后页面的推进关系。

如果去掉逐字稿后用户不能理解本页要表达什么、为什么可信、与客户决策有什么关系，则该页内部内容质量失败。阅读优先不等于堆文档：每页仍只服务一个主要判断，信息密度以完整但不过载为准。

### 6.3 每页完整投影字段

每个 `SlidePlan` 在侧边栏必须同时展示：

- 页码和结论型标题；
- 这一页为什么存在；
- 希望客户形成的判断；
- 页面全部实际文字；
- 实际 PPT 页面、案例页、截图、照片、图表或其他图片材料；
- 材料来源的案例/文件、页码或区域；
- 具体使用哪块内容、支撑什么主张；
- 处理方式：原样引用、裁切、摘要、重绘、脱敏或待补；
- 事实身份和证据缺口；
- 完整逐字稿；
- 阅读质量、信息密度和相邻页面关系；
- 明确的“待你判断”；
- 本页审核判断、意见和处理状态。

若尚未有最终 PPT 页面，右栏显示计划使用的真实材料本体与标注区域，不用通用占位图或纯文字描述冒充材料。

## 7. 最大宽度侧边栏布局

### 7.1 宽度合同

- 以宿主允许的最大侧边栏宽度为主要设计目标，正文容器 `width: 100%`，不设置居中窄列上限，不浪费左右空白。
- 在约 900px 及以上采用双栏：左侧约 43% 为页面目标、客户判断和完整实际文字；右侧约 57% 为真实页面/材料、来源、使用方式和证据缺口。
- 逐字稿、阅读质量、跨页关系、待用户判断、审核动作和意见编辑器横跨双栏下方。
- 空间不足时响应式回落单栏；窄屏是兼容状态，不能反向限制最大宽度视图。
- 页面可连续滚动，不以逐页 Tab、轮播、只显示当前页或逐层点击替代全篇阅读。

### 7.2 轻量目录

目录只用于快速定位，不成为主要内容列：

- 顶部用紧凑章节条显示五章或当前实际章节；
- 点击章节定位到对应内容，不改变正文宽度；
- 页面级导航按需展开，标出未判断、意见未保存和已完成状态；
- 提供“定位下一页未判断”；
- 不复制页面正文，不长期占用左侧宽度。

## 8. 逐页判断与意见输入

### 8.1 四种互斥判断

每页只能保留一种当前判断：

1. `approved`：认可本页；
2. `modify`：需要修改；
3. `evidence`：证据不足；
4. `merge-or-delete`：考虑删页/合页。

判断可以在批次提交前更改；更改必须更新完成状态并保留审计事件。旧判断不作为当前有效结论，但历史不可被静默删除。

### 8.2 完成规则

| 判断 | 是否需要意见 | 何时计为本页完成 |
|---|---|---|
| 认可本页 | 不需要 | 点击并成功保存判断后 |
| 需要修改 | 必填 | 判断和非空意见均成功保存后 |
| 证据不足 | 必填 | 判断和非空缺证说明均成功保存后 |
| 考虑删页/合页 | 必填 | 判断和非空删并建议均成功保存后 |

`mark selected` 不等于 `page completed`。三种需要意见的判断若输入未保存、保存失败或意见被清空，本页回到未完成。

### 8.3 就地意见编辑器

点击三种需要意见的判断后，在当前页底部就地展开输入框，不使用遮挡正文的模态框。

- 修改：`P02 · 需要怎么修改？`，引导说明哪里不对、希望改成什么、必须保持什么。
- 缺证：`P15 · 缺少什么证据？`，引导说明要证明的主张、需要的材料类型、可接受的降级方式。
- 删并：`P21 · 你希望如何删页或合页？`，引导说明删除还是合并、目标页、原因、必须保留和希望删除的内容。

输入最多 1200 字；空白意见不得保存。保存后在当前页回显类型与全文，并提供 `编辑意见`。保存只持久化审核意见，不触发 Codex 新回合，不自动修改蓝图。

### 8.4 结构化页面审核对象

```json
{
  "pageDecisionId": "uuid",
  "reviewBatchId": "uuid",
  "projectId": "uuid",
  "reviewType": "content",
  "sourceVersion": "content-blueprint-v3",
  "slideId": "slide-02",
  "slideOrder": 2,
  "slideTitleSnapshot": "我们以工业场景与工程交付为根基，服务制造企业数字化转型",
  "visibleCopySnapshotRef": "artifact-ref",
  "decision": "approved|modify|evidence|merge-or-delete",
  "comment": "string|null",
  "relatedSlideRefs": [],
  "status": "draft|saved-incomplete|completed|submitted|governed|resolved",
  "createdAt": "ISO-8601",
  "updatedAt": "ISO-8601"
}
```

`visibleCopySnapshotRef` 和页面标题快照用于防止版本变化后意见失去上下文；真实内容仍由 sourceVersion 指向的不可变 ContentBlueprint 提供，不复制为第二套真相。

## 9. 连续审核与批次提交

### 9.1 审核期间只记录

用户连续审核时：

- 保存判断和意见后直接继续下一页；
- 不触发 Codex；
- 不运行反馈治理；
- 不生成 ContentChangeSet；
- 不重写当前 ContentBlueprint；
- 当前 sourceVersion 保持固定。

页头和目录显示：`已完成判断页数 / 总页数`、未完成页数、未保存意见数和已保存意见数。

### 9.2 全页完成硬条件

只有同时满足以下条件，`完成本轮审核，交给 Codex 集中处理` 才启用：

1. 当前 sourceVersion 的全部页面都存在 `completed` 判断；
2. `modify`、`evidence`、`merge-or-delete` 均有已保存的非空意见；
3. 没有打开且包含未保存文字的编辑器；
4. 没有标记保存失败或 revision/sourceVersion 冲突；
5. 当前页面数量与批次预期总页数一致。

未满足时按钮禁用并显示具体缺口，例如：`还剩 6 页未判断 · 2 条意见尚未保存`。

### 9.3 批次提交与冻结

提交后形成不可变 `ContentReviewBatch`：

```json
{
  "reviewBatchId": "uuid",
  "projectId": "uuid",
  "sourceVersion": "content-blueprint-v3",
  "expectedSlideCount": 29,
  "decisionRefs": [],
  "counts": {
    "approved": 18,
    "modify": 6,
    "evidence": 3,
    "mergeOrDelete": 2
  },
  "status": "draft|ready|submitted|plan-proposed|plan-confirmed|applied|superseded",
  "submittedAt": "ISO-8601",
  "submittedBy": "user-action-ref"
}
```

提交动作只冻结批次并触发一个 Codex 后续回合；不确认 G0，不直接生成新蓝图。提交后如需改变意见，必须撤回尚未进入执行的批次并生成新批次版本，不原地改写已提交批次。

## 10. Codex 集中处理

### 10.1 先提出修改方案

Codex 读取冻结批次、当前完整蓝图、框架、证据地图和相邻页面关系，先输出 `ContentBatchRevisionPlan`，至少说明：

- 哪些意见可直接执行；
- 哪些意见会联动其他页面或章节；
- 哪些页面删除或合并，保留什么、删除什么；
- 哪些主张因缺证需要补材料、降级身份、弱化表达或删除；
- 修改后的章节结构、页序和预计页数；
- 保持不变的内容；
- 相互冲突的用户意见、专业风险和需要用户裁决的事项；
- 执行后的复审范围。

Codex 不逐条照办。它必须先做跨页、跨章节、证据和决策逻辑分析，但不得把用户意见自动扩大成跨项目经验或稳定规则。

### 10.2 用户确认修改方案

用户在 Codex 对话中可以继续讨论，直到明确认可 `ContentBatchRevisionPlan`。方案确认：

- 绑定当前 reviewBatchId 和 planVersion；
- 只授权应用本批次方案；
- 不是 G0；
- 不允许复用为任务书、框架或其他批次的确认凭据。

只有确认后，系统才生成相应 FeedbackGovernanceRecord、ContentChangeSet，修改蓝图并按影响范围复审。

### 10.3 新版本复审

- 新版本是新的不可变 ContentBlueprint，例如 v4，不覆盖 v3。
- v3、本轮判断、意见、修改方案、用户确认和执行结果继续保留。
- v4 不自动继承 v3 的已认可状态，因为正文、页序或相邻关系可能变化。
- v4 每页可显示上一轮意见及处理结果，帮助用户验证是否改对，但用户仍须对 v4 全部页面重新判断。
- v4 内部内容质量通过后才进入下一轮侧边栏全稿审核。

## 11. Browser 辅助能力

内容蓝图侧边栏中的图片和来源已经足够完成普通审核；只有需要更大画布时打开 Browser：

- 放大当前案例页、截图、图表或原始 PPT/PDF 页面；
- 显示使用区域或裁切边界；
- 并排比较当前页与来源页、两份案例或相邻页面；
- 查看跨页关系图或高密度源文件。

Browser 与侧边栏共享 sourceVersion、slideId 和 materialRef。关闭 Browser 不改变审核判断；Browser 中不再另建一套内容页级判断和提交按钮。G3 视觉合同 Browser 审阅仍按既有合同运行。

## 12. 系统组件与数据流

### 12.1 组件边界

- `FrameworkDiscussionService`：管理目录草案、框架版本、确认凭据和逐页展开授权。
- `ContentReviewProjectionService`：把内部通过的完整 ContentBlueprint 投影为最大宽度侧边栏连续文档。
- `PageDecisionService`：校验四种判断、三类必填意见、页面完成状态和并发写入。
- `ContentReviewBatchService`：计算全页完成、冻结/撤回批次、触发 Codex 后续回合。
- `ContentBatchPlanningService`：编译批次上下文，生成版本化整体修改方案，等待用户确认。
- `BlueprintEngine`：只消费已确认方案对应的治理记录和 ContentChangeSet，生成新蓝图并复审。
- `BrowserEvidenceAdapter`：只打开选定材料/页面的辅助视图，不保存第二份判断状态。

### 12.2 数据流

```text
Codex 框架讨论
  → FrameworkDraft / FrameworkConfirmation
  → BlueprintEngine 生成完整蓝图并内部审查
  → Sidebar ContentReviewProjection
  → PageDecisionService 持久化判断与意见
  → ContentReviewBatchService 校验全部页面并冻结
  → Codex + ContentBatchPlanningService 提出修改方案
  → 用户在 Codex 确认方案
  → FeedbackGovernanceRecord + ContentChangeSet
  → BlueprintEngine 生成新版本并复审
  → Sidebar 新一轮全稿审核
```

## 13. 工具合同变更

建议新增或收紧以下能力；具体工具名可在实现计划中与现有 v1.6 MCP 合同对齐，但业务语义不得丢失：

- `save_content_framework_draft`：保存框架草案，不生成逐页内容。
- `confirm_content_framework`：保存真实用户框架确认凭据；不确认 G0。
- `authorize_full_deck_expansion`：绑定当前框架版本，授权生成完整逐页规划。
- `get_content_sidebar_review_projection`：返回完整全稿侧边栏投影，不返回摘要版替代物。
- `save_content_page_decision`：原子保存单页判断与可选/必填意见，返回 pageCompletion 和批次统计。
- `submit_content_review_batch`：仅在全页完成时冻结批次并返回 Codex follow-up message；不得直接生成 ContentChangeSet 或确认 G0。
- `save_content_batch_revision_plan`：保存 Codex 提出的整体修改方案。
- `confirm_content_batch_revision_plan`：记录真实用户方案确认；随后才允许治理和修改。
- `open_content_evidence_browser`：按当前项目、版本、页面和材料引用打开受限辅助 Browser。

所有写工具必须带 `expectedRevision`、sourceVersion 和稳定 error code；React/侧边栏宿主、Node MCP 或 Codex Prompt 均不能绕过 Python 服务校验。

## 14. 错误与恢复

| 错误码 | 条件 | 恢复方式 |
|---|---|---|
| `CONTENT_FRAMEWORK_NOT_CONFIRMED` | 试图在框架未确认前生成/读取逐页内容 | 返回当前框架和一个最高影响问题 |
| `FULL_DECK_EXPANSION_NOT_AUTHORIZED` | 框架已确认但未获逐页展开授权 | 等待用户明确授权，不把继续/OK 自动复用为授权 |
| `CONTENT_PAGE_COMMENT_REQUIRED` | 三种需意见判断缺少非空意见 | 保留选择和草稿，本页不计完成 |
| `CONTENT_PAGE_DECISION_INCOMPLETE` | 判断未保存、意见未保存或保存失败 | 定位本页并继续编辑/重试 |
| `CONTENT_REVIEW_BATCH_INCOMPLETE` | 存在未完成页面或未保存意见 | 返回准确数量和下一未完成页 |
| `CONTENT_REVIEW_BATCH_STALE` | 页面数量、sourceVersion 或 revision 与批次不一致 | 保留输入，重新绑定或创建新批次 |
| `CONTENT_REVIEW_BATCH_FROZEN` | 试图修改已提交批次 | 撤回未执行批次或新建批次版本 |
| `CONTENT_BATCH_PLAN_NOT_CONFIRMED` | 试图在方案未确认前改稿 | 保留原蓝图和批次，回到 Codex 讨论方案 |
| `CONTENT_REVIEW_SAVE_FAILED` | 判断/意见持久化失败 | 保留编辑器草稿并幂等重试 |
| `CONTENT_REVIEW_CONFLICT` | 同页判断或蓝图版本并发变化 | 展示当前值和冲突范围，不静默覆盖 |

失败不得清空用户输入、改变当前 sourceVersion、自动降低判断完成条件或跳过修改方案确认。

## 15. 验收标准

### 15.1 阶段边界

1. 框架未确认时，侧边栏和 Browser 均无逐页内容、材料计划、逐字稿和逐页判断。
2. 框架确认与逐页展开授权分别有凭据，任一缺失均不能生成用户可审全稿。
3. 展开授权、批次提交、修改方案确认和 G0 是四个不同动作，不能互相复用。

### 15.2 完整阅读

4. 当前 ContentBlueprint 的所有页面按最终顺序连续展示，页面数与源产物一致。
5. 每页全部实际文字逐字段、逐字可见；无摘要替代、截断、省略号和逐页切换依赖。
6. 每页同时显示目标、客户判断、真实材料本体、来源定位、使用方式、证据身份/缺口、逐字稿、阅读质量和跨页关系。
7. 去掉逐字稿后页面仍能独立形成主张—理由—证据—边界链条；不满足时内部内容质量失败。
8. 最大宽度视图占满侧边栏可用宽度，宽屏双栏、窄屏单栏，任何目标视口无横向溢出。

### 15.3 审核交互

9. 四种判断互斥且可修改；三种需意见判断均在当前页就地展开编辑器。
10. 空白意见不能保存；未保存或保存失败时本页不计完成，草稿不丢失。
11. 保存单页判断不会触发 Codex、反馈治理、改稿或 sourceVersion 变化。
12. 目录能定位下一未完成页，并准确区分未判断、意见未保存和完成。
13. 全部页面未完成时批次按钮禁用并说明缺口；全部完成且无冲突后才启用。
14. 批次提交后判断和意见被冻结，并保存项目、sourceVersion、页面快照引用、计数和真实用户动作引用。

### 15.4 集中处理与版本

15. 提交批次后 Codex 先形成整体修改方案，不直接生成新版蓝图。
16. 修改方案覆盖直接修改、跨页联动、删并、缺证降级、页数变化、保持不变项、冲突和复审范围。
17. 用户未确认方案时，任何 ContentChangeSet 或新 ContentBlueprint 写入被 Python 服务拒绝。
18. 方案确认后生成新不可变版本并按影响范围复审；旧版本、批次和方案保留。
19. 新版本不继承旧页的认可状态，全部页面重新判断；上一轮处理结果可作为辅助上下文。
20. 批次提交与方案确认均不等于 G0；只有最终全稿审核后，用户在 Codex 对话明确确认 G0 才进入视觉阶段。

### 15.5 表面分工

21. 内容蓝图完整审核可在最大宽度侧边栏独立完成；Browser 不是唯一入口。
22. Browser 可放大和比较材料，但不建立第二套内容判断状态。
23. G3 视觉合同仍使用 Browser 专业审阅，本次变更不把视觉合同搬入侧边栏。
24. 聊天、侧边栏和 Browser 读取同一项目 revision/sourceVersion，不形成第二业务真相源。

## 16. 对现有基线的明确变更

本设计取代以下旧合同，仅限 UI-03 内容蓝图阶段：

1. **取代“侧边栏只允许轻量状态投影，禁止完整合同”。** 内容蓝图在框架确认并获得逐页展开授权后，侧边栏必须承载完整全稿；项目总览、材料、视觉生产和交付仍可保持轻量投影。
2. **取代“内容蓝图完整审核只在 Codex 内置 Browser”。** 内容审核以侧边栏为主；Browser 为可选证据辅助。G3 视觉合同仍保留 Browser。
3. **取代“内容审阅无需逐页完成即可继续”。** 用户可以自由连续阅读，但提交集中处理前必须完成全部页面判断；这不是生产阶段的逐页等待，也不新增 Gate。
4. **取代“专业审阅页右上角保存标记是唯一强主操作”。** 内容蓝图侧边栏允许逐页保存，并在全部完成后显示 `完成本轮审核，交给 Codex 集中处理`；Browser 视觉合同原规则不变。
5. **收紧反馈时序。** 单页保存只记录，不立即形成 FeedbackGovernanceRecord；整批提交并由 Codex 提出修改方案、用户确认后，才进入正式反馈治理和 ContentChangeSet。

## 17. 明确不做

- 不把侧边栏做成状态仪表盘、当前页摘要或缩略图目录。
- 不在框架未确认前生成“占位逐页内容”。
- 不用目录、AI 总体体检或少数代表页替代完整全稿。
- 不让用户逐页等待 AI 生成；完整规划一次生成，审核可连续进行。
- 不在保存一条意见后立即改稿。
- 不在批次提交后绕过修改方案确认直接重写。
- 不把页面做成传统 PPT 文本和图形编辑器。
- 不在内容蓝图阶段提前讨论视觉风格、页面布局或配色。
- 不迁移 G3 视觉合同的 Browser 审阅合同，不扩展为独立 Web 产品。
- 不把历史重庆机电案例的内容、图片或结论写入当前真实项目。

## 18. 待实现计划决定的技术细节

以下为实现层选择，不影响已经确认的产品合同：

- 宿主最大侧边栏的实际宽度范围和稳定挂载 API；
- 当前 React 投影如何拆分长文档、图片懒加载和 60+ 页性能；
- `PageDecision` 是扩展 ReviewMarkSet 还是独立聚合并由兼容投影桥接；
- 批次撤回在 `plan-proposed` 后是否允许，还是必须新建替代批次；
- 相关页引用采用显式选择控件还是先从自然语言中结构化提取；
- Browser 辅助视图复用现有 Review Bridge 还是使用受限的资产比较 route。

任何技术选择都不得降低全文完整性、全页完成硬条件、批次冻结、修改方案确认、单真相源和 G0 前内容优先边界。
